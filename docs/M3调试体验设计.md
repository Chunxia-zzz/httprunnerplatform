## 0. 最关键的引擎事实（决定了 M3 怎么做）

实测记录 A2 已经钉死了一件事：

> **hrp 的最小执行单位是「一个用例文件」。没有「只跑第 N 步」的开关。**

`hrp run <目录>` 是「全有或全无」：要么跑整个目录的所有用例，要么什么都不跑；
断言失败会 panic 让整个进程死亡（F8）。

由此推出 M3 调试能力的两条实现路径，**都不需要改引擎**：

| 能力 | 实现方式 | 是否复用现有代码 |
|:---|:---|:---|
| **整用例试跑** | 复用 `POST /runs`（`target_type=case`） | ✅ 基本已具备，M3 只需前端接「试跑」入口 |
| **单步骤调试** | 平台**临时构造一个「只含该步骤」的最小用例**，编译成 YAML，跑一个独立子进程，跑完即弃 | 复用 compiler 的 `renderStep` + executor 的 `RunCase` |

「单步调试 = 临时造最小用例」是整个 M3 的技术支点，也是唯一需要新写的执行侧逻辑。

## 1. 已确认的决策

| # | 决策项 | 结论 | 理由 |
|:---:|:---|:---|:---|
| 1 | 单步调试的实现 | **临时构造最小用例**，不落库、不进执行历史 | hrp 无「只跑单步」开关；临时用例跑完即弃，避免污染执行记录与通过率分母 |
| 2 | 单步调试是否写执行历史 | **不写** | 调试是「编辑器的探测动作」，不是「执行」；写进去会稀释 `runs` 列表与通过率统计 |
| 3 | 单步调试的变量上下文 | **带上用例 config.variables + 该步骤之前所有步骤的 extract** | 否则「依赖上一步提取的 token」的步骤永远调试不了 —— 那才是用户最想调试的场景 |
| 4 | 参数化 `debugtalk.py` 自定义函数 | **M1–M4 不支持**（沿用 C12） | 实测 venv+funppy 安装失败、插件路径无限挂起；用列表/CSV 两种来源已覆盖 95% 需求 |
| 5 | 源码视图可编辑 | **保存时严格反解析回结构化，失败即拒存** | 唯一风险入口，必须闭环（方案 4.2） |
| 6 | 断言配置器 | **硬绑内置校验器清单** | 引擎断言不支持自定义拓展（方案 3.3） |

## 2. ③-a 单步调试（P0，本片核心）

### 2.1 目标与验收

> 验收 ①：**不跑完整个用例就能验证单个步骤（≤3 次点击）**。
> 3 次点击 = 「① 选中步骤 → ② 点调试 → ③ 看请求/响应/断言结果」。

### 2.2 后端：`POST /cases/{id}/debug` 与 `POST /steps/{id}/debug`

两个入口，同一个底层：

- **整用例试跑** `POST /cases/{id}/debug`：语义上等价于「临时执行一次」，但**同步阻塞**返回结果（不像 `POST /runs` 异步返回 run_id），因为调试要的是「当场看到」，不是「去执行记录里翻」。
- **单步调试** `POST /steps/{id}/debug`：构造最小用例，同步阻塞返回。

#### 同步 vs 异步

`POST /runs` 是异步（返回 run_id，走执行记录），因为团队执行可能要几分钟、要进度、要落库。
**调试必须是同步**：用户在编辑器里点了调试，期望 3 秒内看到结果，而不是跳去等一个队列。
但同步有上限 —— 引擎跑一条用例通常 1~5 秒，设 **30 秒超时**（超过就返回「已启动但超时」并给轮询地址，兜底）。

#### 最小用例构造（单步调试的核心）

给定步骤 `S`（第 `k` 步），构造一个「只有 `S` 一个步骤」的用例：

```
config:
  name: "调试 · <case.name> · <step.name>"
  variables: <case.config.variables>      # 带上用例级变量
  verify: false
teststeps:
  - <S 的完整步骤定义>
```

**变量上下文**（决策 3）：步骤 `S` 里引用了 `$token`，而 `token` 是第 `k-1` 步 extract 出来的。
如果不带上前面步骤的提取，`$token` 就是未定义变量，调试必然失败 —— 而「依赖上一步提取」恰恰是最需要调试的场景。

因此构造最小用例时，**把 `1..k-1` 步的 `extract` 全部前移为用例级变量**：

| 来源 | 做法 |
|:---|:---|
| `case.config.variables` | 原样带上 |
| 第 1..k-1 步的 `extract` | **跑一遍这 k-1 步**（真正的「前置执行」），把提取结果注入为变量 |

这里有两个选择，**默认取「真实前置执行」**：

- **A. 真实前置执行**：把 `1..k-1` 步也编进最小用例（作为 `teststeps` 的前缀），让引擎真的跑一遍，提取自然生效。✅ 准确，变量值是真实的。代价：耗时等于跑 k 步。
- **B. 静态注入占位**：只把 `extract` 的变量名声明为变量，值给空。❌ `$token` 会变成空字符串，断言必然失败，等于调试了个寂寞。

**结论：默认 A。** 用户点「调试第 k 步」，平台实际上跑「第 1..k 步」（截断版），把第 k 步的请求/响应/断言单独展示。前端要如实标注「本次调试实际执行了前 k 步」。

> 例外：若用户明确只调试一个**不依赖任何提取**的步骤（如「登录」第一步），
> 最小用例就只有一个步骤，零额外开销。

#### 返回结构

```json
{
  "code": 0,
  "data": {
    "debug_id": "tmp_xxxx",          // 本次调试的临时标识，不落库
    "executed_steps": 3,             // 实际执行了几步（含前置）
    "target_step_seq": 3,            // 用户真正要调试的那一步
    "final_url": "http://.../login/", // ⭐ 最终生效 URL（C9，非 YAML 原文）
    "status": "pass",
    "elapsed_ms": 412,
    "request": { "method": "POST", "url": "...", "headers": {...}, "body": "..." },
    "response": { "status_code": 200, "headers": {...}, "body": "..." },
    "assertions": [ { "check": "status_code", "assert": "eq", "expect": 200, "passed": true, "actual": 200 } ],
    "extract_result": { "token": "eyJ..." },   // 本步提取出的变量
    "error_msg": ""
  }
}
```

关键点：**请求/响应快照直接取自引擎的 stdout 报文（或 summary.json 的 `req_resps`）**，
复用 parser 现有的快照提取逻辑，不新造轮子。

### 2.3 前端：编辑器内的「调试」入口

- 步骤卡片上每个步骤加一个「▶ 调试」按钮（≤3 点击的第 1 点）；
- 点后弹一个**调试结果面板**（抽屉或侧栏），展示请求/响应原文 + 断言逐条结果 + 最终生效 URL；
- 「整用例试跑」按钮放在编辑器顶部。

### 2.4 工作量预估

| 部分 | 内容 | 规模 |
|:---|:---|:---|
| 后端 | `debug` handler + 最小用例构造 + 同步执行封装 + 快照提取复用 | 中 |
| 前端 | 调试按钮 + 结果面板 | 中 |

## 3. ③-b 参数化（P1）

### 3.1 目标与验收

> 验收 ②：**CSV 参数化能按 `limit`/`pick_order` 正确迭代**。

### 3.2 数据模型（已建表，直接启用）

`param_dataset` 表 M1 已建（`Source: list|csv`、`Inline`、`CsvPath`、`Strategy`、`Limit`）。
M3 启用它：

- `Source=list`：`Inline` 存列表（如 `[{username,password}, ...]`）；
- `Source=csv`：`CsvPath` 指向项目工作区下的 `data/{code}.csv`，前端上传时写盘。

### 3.3 与用例的关联

用例的 `config.parameters` 引用数据集。httprunner 原生支持两种写法，**平台只开放「引用数据集」这一种**，隐藏 `${parameterize($file)}` 的原始写法：

```yaml
config:
  parameters:
    - dataset_name: 用户登录数据        # 平台层语义，编译时转成 hrp 能懂的参数
```

编译时由 compiler 把 `ParamDataset` 转成 hrp 的参数化格式（列表直接内联，CSV 用 `parameterize`）。

### 3.4 迭代策略

| 策略 | 说明 | 默认 |
|:---|:---|:---|
| `sequential` | 按顺序取 | ✅ 默认 |
| `random` | 随机 | |
| `unique` | 不重复 | |

`limit` 控制最多迭代几组（0 = 全部）。

### 3.5 前端

- **参数集管理页**：列表 + 新建（列表式直接填表格 / CSV 上传）；
- **用例编辑器**：`config.parameters` 处选数据集 + 策略 + limit。

## 4. ③-c 断言配置器 + 源码视图 + 变量依赖提示

### 4.1 断言配置器

现在断言是**表单里手填 `check`/`assert`/`expect` 三个字段**。M3 做成可视化：

- `assert`（校验器）→ 下拉，硬绑 `ASSERT_METHODS` 清单（前端 `dict.ts` 已有 20 个）；
- `expect` → 输入框 + **自动推断类型**（填 `200` 推断为 int，填 `"ok"` 推断为 str）；
- 从 UI 层杜绝「YAML 手写缩进/类型错误」。

### 4.2 源码视图可编辑（风险最高的改动）

- Monaco 现在 M1 是**只读**展示 YAML。M3 开可编辑；
- **保存时严格反解析回结构化数据**：YAML → 结构化 `TestCase`，任何解析失败（非法 YAML、字段类型错）→ **拒绝保存** + 高亮报错行；
- 反解析失败意味着「用户在源码里写了表单表达不了的东西」，必须让他改回，而不是静默丢弃。

### 4.3 变量依赖提示

- 步骤里引用 `$token`，编辑器检查它是否由「前面步骤的 extract 或用例 variables」提供；
- 未定义 → 红色标记 + 悬停提示「未定义变量」（对应引擎退出码 21）；
- 这是方案 3.3 明确的「工作量最大的单一模块」：优先级解析 + `${}` 边界识别 + `$$` 转义三件套。

## 5. 建议的实施顺序与拆分

| 片 | 内容 | 依赖 | 风险 |
|:---|:---|:---|:---|
| **③-a** | 单步调试（后端 + 前端结果面板） | 无 | 低（复用 compiler/executor/parser） |
| **③-b** | 参数化（数据集管理 + 编译转换 + 迭代） | 无 | 中（编译转换要测 CSV 路径） |
| **③-c** | 断言配置器 + 源码可编辑 + 变量依赖 | ③-a（调试要展示断言结果） | **高**（源码反解析是闭环难点） |

**建议从 ③-a 单步调试开始**：它是 M3 的验收标准 ①，技术路径清晰，复用最多，能最快验证「临时造最小用例」这条支点是否成立。

## 6. 需要你拍板的点

1. **单步调试的「前置执行」策略**：默认 A（真实跑前 k-1 步拿真实变量值）。要不要提供「只看单步、忽略依赖」的 B 选项（变量给空）？我建议**不做 B**（给空值调试没意义），只做 A。
2. **同步阻塞超时**：默认 30 秒。可接受吗？（调试正常 1~5 秒，30 秒是兜底）
3. **参数化的 CSV 上传**：默认存项目工作区 `data/{code}.csv`（跟随方案 3.4 的目录结构），还是存 DB？我建议**存文件**（httprunner 参数化读的就是文件）。
4. **M3 范围确认**：方案 10.1 里 M3 还含「用例标签/优先级/模块/检索」——但这一项在 M1 已经做了（用例列表有模块树 + 筛选）。确认 M3 不需要重做它，只做「调试 + 参数化 + 断言配置器 + 源码视图 + 变量依赖」这五件。

## 8. 实施记录（已落地）

> 三片全部完成并验收通过。关键实测结论沉淀在 `docs/引擎实测记录.md`（A22 参数化语法）。

### ③-a 单步调试 ✅

- `internal/service/debug.go`（临时最小用例）+ `handler_debug.go` + `POST /cases/{id}/debug`。
- 前端 `DebugPanel.vue` + 步骤卡片「调试此步」按钮。
- 验收：smoke-debug 14 项 + CDP debug-smoke 11 项全绿（含「第 1 步提取 token，第 2 步可用」的变量依赖验证）。

### ③-b 参数化 ✅

- `internal/service/param.go`（数据集 CRUD）+ `compiler/parameters.go`（编译转换）+ `handler_param.go`。
- 平台层格式 `config.datasets = [{name, limit}]`，独立键；编译时转引擎语法。
- 关键实测（A22）：`- parameterize: file.csv` 写法 v4.3.6 静默丢弃；正确 CSV 写法是 `col1-col2: "${P(data/xxx.csv)}"`；关联参数内联写法成对迭代（非笛卡尔积）；引擎无 limit 开关 → 平台编译期裁剪。
- 前端 `ParamListView.vue`（参数集管理）+ 用例编辑器「数据集」tab。
- 验收：compiler 15 项单测 + smoke-param 28 项 + CDP param-smoke 16 项全绿（CSV 3 行 → 3 次迭代对账 step_total）。

### ③-c 断言配置器 + 源码可编辑 + 变量依赖 ✅

- **断言配置器**：M1 已实现（`AssertEditor.vue` 下拉 + 类型推断 + 编译预览），③-c 仅验收通过。
- **源码可编辑**：`internal/decompiler/`（YAML → CaseReq 反解析）+ `PUT /cases/{id}/yaml`（SaveYAML）。
  反解析失败带行号（`decompiler.LineError`），前端 `YamlPreview.vue` 红标高亮报错行。
  已知信息损失：请求头三层归属、verify 来源不可还原（直接编辑编译产物的固有代价）。
- **变量依赖提示**：前端 `utils/variables.ts` 三件套（`$name` 识别 + `${}` 边界 + `$$` 转义）+ `CaseEditorView` 跨步骤作用域计算 + `StepEditor` 未定义标红。
  后端 validator 的 `UNDEFINED_VARIABLE`（M1 已有，含环境变量）作权威兜底，前端为编辑期实时提示。
- 验收：decompiler 单测 8 项 + smoke-yaml-save 11 项 + CDP m3c-smoke 9 项全绿。

### 关键设计取舍（拍板结果）

1. 单步调试：只做方案 A（真实跑前置步骤），同步超时默认 30s 上限 5min。
2. 参数化 CSV 存项目工作区文件（非 DB），派生文件为编译产物（可再生）。
3. 源码视图用**轻量 textarea**（非 Monaco），反解析后端完整交付闭环。
4. M3 不含「用例标签/优先级/模块/检索」（M1 已做）。
