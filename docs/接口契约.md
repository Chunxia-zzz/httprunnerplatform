## 0. 通用约定

| 项 | 约定 |
|:---|:---|
| 统一前缀 | `/api/v1` |
| CI 触发前缀 | `/open`（Token 鉴权，M2） |
| 编码 | 请求与响应均为 `application/json; charset=utf-8` |
| 认证 | M1 沿用登录会话（Cookie `hrp_session`）；M2 增加 `api_token` |
| 分页 | 请求 `?page=1&page_size=20`，响应 `data: { list, total, page, page_size }` |
| 时间格式 | RFC3339（`2026-09-22T17:30:00+08:00`），统一携带时区 |
| 长文本 | 快照类字段（请求/响应原文、原始日志）在**列表接口中不返回**，仅详情接口返回 |
| 幂等 | 除执行类接口外，PUT 为全量覆盖语义 |

### 0.1 统一响应体

```jsonc
// 成功
{ "code": 0, "message": "ok", "data": { /* ... */ } }

// 失败
{ "code": 40001, "message": "用例名称已存在", "data": null }
```

`code == 0` 表示业务成功。**HTTP 状态码与业务 code 同时使用**：

| HTTP | 场景 |
|:---:|:---|
| 200 | 业务正常（含业务校验失败，此时 `code != 0`） |
| 400 | 参数格式错误（JSON 不合法、必填缺失） |
| 401 | 未登录 / 会话失效 |
| 403 | 无权限（非管理员执行管理员操作） |
| 404 | 资源不存在 |
| 500 | 服务端内部错误 |

### 0.2 错误码

| code | message | 说明 |
|:---|:---|:---|
| 0 | ok | 成功 |
| 40000 | 参数错误 | 通用参数问题 |
| 40001 | 资源名称/标识已存在 | 唯一约束冲突 |
| 40002 | 资源不存在 | |
| 40003 | 资源被占用，无法删除 | 如用例被用例集引用 |
| 40004 | 非法标识符 | `code` 不满足 `^[a-zA-Z0-9_-]{1,64}$` |
| 40010 | 存在未保存的变更冲突 | 乐观锁场景（M1 暂不启用） |
| 40100 | 未登录 | |
| 40300 | 无权限 | |
| 50000 | 服务端内部错误 | |
| 50001 | 引擎不可用 | hrp 二进制未找到或版本探测失败 |
| 50002 | 工作区操作失败 | 创建/复制工作区失败 |
| 50003 | 编译失败 | 编译器产出失败（含 config.name 重复） |
| 50004 | 校验未通过 | 静态校验发现问题，`data` 携带问题列表 |
| 50005 | 执行器错误 | 子进程启动/超时/取消异常 |
| 50006 | 报告不存在 | HTML 报告未产出（如断言失败时，见 F8） |

> **`50004` 的 `data` 结构是校验器的对外契约**，见 3.4。

## 1. 认证与账号

角色只有两档：`admin`（可管理账号、可删除项目）与 `member`（其余功能全部可用）。
**不引入 RBAC** —— 10 人团队里多一层权限模型带来的沟通成本高于收益。

### POST /api/v1/auth/login

```jsonc
// 请求
{ "username": "admin", "password": "admin123" }
// 响应
{ "code": 0, "data": { "user_id": 1, "username": "admin", "nickname": "管理员", "role": "admin" } }
```

设置 Cookie `hrp_session`（HttpOnly）。

失败一律返回 `40000`，**不区分「用户不存在」与「密码错误」**，避免账号枚举。
被禁用的账号（`enabled=false`）同样走这条错误，不额外提示「你被禁用了」。

### POST /api/v1/auth/logout → `{ "code": 0 }`

### GET /api/v1/auth/me

返回当前用户（结构同登录的 `data`）；未登录时 HTTP 401。

### POST /api/v1/auth/password — 本人修改密码

```jsonc
// 请求
{ "old_password": "admin123", "new_password": "brandnew123" }
// 响应
{ "code": 0, "data": null }
```

成功后 **当前会话保留**、该用户**其它会话全部吊销**。

保留当前会话是刻意的：把发起修改的这台设备也一起登出，用户会以为改密码把账号弄坏了。
旧密码错误 / 新密码不合规 / 新旧相同均返回 `40000`（`message` 可直接展示）。

**密码策略**（两端必须一致，见 `internal/service/user.go` 与 `web/src/utils/password.ts`）：

| 规则 | 说明 |
|:---|:---|
| 长度 ≥ 8，≤ 72 **字节** | 按字节算：`bcrypt` 会**静默截断**超过 72 字节的输入，不拦就会出现"设了 100 位密码只有前 72 位生效" |
| 不含空白（空格 / `\t` / `\r` / `\n`） | 与 Go 的 `strings.ContainsAny(pw, " \t\r\n")` 严格对齐 |
| 不等于用户名（大小写不敏感） | |
| 不在弱密码表内 | 表**只在前端不复制**：后端是唯一真源，前端多存一份必然漂移 |

### 账号管理（`/api/v1/users`，整组 `RequireAdmin`）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| GET | `/api/v1/users` | 列表，支持 `keyword`（匹配账号或昵称）与 `role` 过滤 |
| POST | `/api/v1/users` | 新建账号 |
| PUT | `/api/v1/users/{id}` | 改昵称 / 角色 / 启用状态 |
| DELETE | `/api/v1/users/{id}` | 软删除 |
| POST | `/api/v1/users/{id}/password` | 管理员重置密码（无需旧密码） |

非管理员访问以上任意端点：HTTP **403** + `40300`。

```jsonc
// GET /api/v1/users 响应
{ "code": 0, "data": { "list": [ {
  "id": 1, "username": "admin", "nickname": "管理员",
  "role": "admin", "enabled": true,
  "online_sessions": 2,        // 该账号当前有效会话数
  "created_at": "2026-09-23 00:41:37"
} ], "total": 2, "page": 1, "page_size": 20 } }

// POST /api/v1/users 请求
{ "username": "zhangsan", "password": "initpass123", "nickname": "张三",
  "role": "member", "enabled": true }   // nickname/role/enabled 可省；role 默认 member，enabled 默认 true

// PUT /api/v1/users/{id} 请求（三个字段都可省，省 = 保持原值）
{ "nickname": "张三", "role": "member", "enabled": false }

// POST /api/v1/users/{id}/password 请求
{ "password": "resetpass123" }
```

**`PUT /api/v1/users/{id}` 刻意没有 `username` 字段**：用户名是登录标识，且会写进
`run_record.trigger_by` 关联的历史，允许改名等于让历史记录悄悄换人。要换名字就新建账号、停用旧账号。

**用户名归一化**：写入前转小写并去空白，因此 `Admin` 与 `admin` 是同一个账号（重复时返回 `40001`）。
合法字符 `^[A-Za-z0-9][A-Za-z0-9._@-]{1,63}$`，便于直接用邮箱当账号。

#### 三条守卫（违反均返回 `40300`，`message` 可直接展示）

1. **不能对自己下手**：不能删自己、不能把自己降级、不能禁用自己。
2. **不能干掉最后一个可用管理员**：判据是 `role=admin 且 enabled=true`。
   只数 `role=admin` 会把系统锁死在"有一个管理员但登不进去"的状态。
   唯一可用管理员同样不能被删除。
3. **重置密码不能作用于自己**：那条路径不验旧密码，否则"忘记旧密码"就成了绕过旧密码校验的后门。
   改自己的密码请走 `POST /auth/password`。

#### ⭐ 权限变更必须吊销会话（本模块最容易漏掉的一条）

`online_sessions` 归零是「吊销真的发生了」的**可见证据**，不是装饰字段。

会话表里缓存着 `Principal`（含 `role`），中间件信任这份缓存。因此：

| 动作 | 对会话的影响 |
|:---|:---|
| 改**角色** | 吊销该用户**全部**会话 |
| 改**启用状态** | 吊销该用户**全部**会话 |
| 重置**密码** | 吊销该用户**全部**会话 |
| 只改**昵称** | **不**吊销，只就地刷新会话里的昵称（否则管理员改个昵称全组被登出） |

不吊销的后果很隐蔽：数据库改对了、页面也刷新了，但被降级的管理员在 TTL（默认 24h）内
**仍然是管理员** —— 改动等于没生效。

## 2A. 用例集（M1.5）

用例集是**扁平**的：一组用例的有序列表，**不支持**「用例集里放用例集」。
理由见 [用例集与测试计划设计.md](用例集与测试计划设计.md) 1.1。

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| GET | `/api/v1/projects/{id}/suites` | 列表，支持 `keyword` |
| POST | `/api/v1/projects/{id}/suites` | 新建 |
| GET | `/api/v1/suites/{id}` | 读取 |
| PUT | `/api/v1/suites/{id}` | 修改（**不含 `code`**，与项目/账号同理） |
| DELETE | `/api/v1/suites/{id}` | 软删除；被计划引用返回 `40003` |
| GET | `/api/v1/suites/{id}/cases` | 成员列表（含「能不能跑」的标注） |
| PUT | `/api/v1/suites/{id}/cases` | **全量替换**成员，数组顺序即执行顺序 |

```jsonc
// POST /api/v1/projects/1/suites 请求
{ "code": "smoke", "name": "冒烟集", "description": "",
  "execute_mode": "sequential", "on_failure": "continue", "timeout": 0 }
// execute_mode / on_failure / timeout 可省；默认值依次为 sequential / continue / 0
// ⚠️ execute_mode=parallel 会被**明确拒绝**（40000），不会悄悄降级成串行。

// PUT /api/v1/suites/1/cases 请求
{ "case_ids": [3, 1, 2] }        // 顺序即执行顺序；空数组 = 清空成员
```

成员校验（违反返回 `40000` / `40001`）：

| 情况 | 处理 |
|:---|:---|
| 同一用例出现两次 | `40001` —— 重复会破坏「通过率的分母」，几乎都是误操作 |
| 用例不存在或不属于本项目 | `40000` —— 不放到执行时才暴露，否则用户只看到「预期 10 条实际 8 条」却不知少了谁 |

`get_on_failure` 成员视图会标出**现在能不能跑**：

```jsonc
{ "seq": 2, "case_id": 7, "case_code": "login", "status": "disabled",
  "runnable": false, "skip_reason": "用例已禁用，执行时记为 skipped" }
```

> 用例被**软删除**后成员行仍在，视图里 `case_code` 为 `(已删除)`、
> `runnable=false`。执行时记为 `error` 而不是静默跳过 ——
> 否则用户只能对着「预期 10 条实际 8 条」猜少了谁。

### 2A.1 执行语义（已实现）

通过 `POST /api/v1/runs` 触发，`target_type` 填 `suite`：

```jsonc
// POST /api/v1/runs
{ "project_id": 1, "target_type": "suite", "target_id": 7, "env_id": 3, "options": {} }
// → { "code": 0, "data": { "run_id": 42, "status": "queued" } }
```

| `target_type` | 含义 | 状态 |
|:---|:---|:---|
| `case`（缺省） | 单用例执行 | ✅ |
| `suite` | 用例集执行 | ✅ |
| `plan` | 测试计划 | ❌ 暂不支持，返回 `40000` |

要点（详见 [用例集与测试计划设计.md](用例集与测试计划设计.md) 第 2 节）：

- 一次用例集执行 = **1 条 `RunRecord(target_type=suite)` + N 条 `CaseResult`**；
- 每个用例**独立编译、独立子进程**（A2 硬约束），邻居用例写坏不挡住本条；
- 串行执行，**成员顺序即执行顺序**；`on_failure` 取用例集自身的配置：
  - `continue`（默认）：某条失败后继续跑，最终状态取最坏值；
  - `abort`：失败后不再跑后面的用例。
- 用例数对账：三者都在 `GET /runs/{id}` 里返回。

#### 对账三字段的口径

| 字段 | 含义 |
|:---|:---|
| `expected_case_count` | **打算让引擎跑的条数**（不含已禁用 / 已删除成员；`abort` 或取消时收缩到已尝试条数） |
| `actual_case_count` | 引擎**真正启动**了的条数 |
| `count_mismatch` | 二者不等，且状态不是 `canceled` |

三者不等时**强制升为 `error`**（沿用实测 F5 的防假绿规则：畸形用例被引擎
静默丢弃时退出码是 0 且 `success=true`，只看退出码会给出假绿）。

`abort` 与取消是「用户主动让后面的不跑」，**不**计入 `count_mismatch`。

## 2C. CI 令牌（M2）

**管理**走会话体系（`/api/v1`），**使用**走令牌（`/open`）。两者分开：
混在一起的话，"谁能签发令牌"会被"令牌能干什么"掩盖掉。

### 2C.1 管理端点（需登录）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| GET | `/api/v1/projects/{id}/tokens` | 列表（只有 `prefix`，没有任何秘密） |
| POST | `/api/v1/projects/{id}/tokens` | 签发，**唯一一次**返回明文 |
| DELETE | `/api/v1/tokens/{id}?project_id={pid}` | 吊销，即刻生效 |

```jsonc
// POST /api/v1/projects/1/tokens
{ "name": "流水线", "scope": "run:trigger,run:read", "ttl_days": 0 }

// 响应 —— ⭐ token 只在这里出现一次
{ "code": 0, "data": {
  "id": 5, "prefix": "hrp_ci_a1b2c3d4", "scope": "run:trigger,run:read",
  "token": "hrp_ci_<64 位 hex>"
} }
```

> - `scope` 留空 = `run:trigger,run:read`；`ttl_days=0` 表示不过期
> - 库里只存 `sha256(明文)`，列表里只有 `prefix`。忘了就重签 ——
>   对 CI 而言重签的成本远低于"明文长期躺在库里"
> - 撤销必须带 `project_id`：否则一个项目的管理员能吊销别人的令牌

### 2C.2 CI 端点（令牌鉴权，前缀 `/open`）

| 项 | 约定 |
|:---|:---|
| 鉴权 | `Authorization: Bearer <token>` 或 `X-HRP-Token: <token>` |
| 触发 | `POST /open/runs` — 请求体与 `/api/v1/runs` 一致 |
| 取结果 | `GET /open/runs/{id}/result` |
| 同步等待 | 默认异步返回 `run_id`；`?wait=1&timeout=<秒>` 阻塞等待（默认上限 5 分钟，最大 30 分钟） |

```jsonc
// GET /open/runs/42/result
{ "code": 0, "data": {
  "run_id": 42, "wait": true, "status": "failed",
  "exit_code_for_ci": 1,          // ⭐ 0 成功 / 1 有用例没过 / 2 没跑完
  "total": 10, "passed": 8, "failed": 2, "error": 0, "skipped": 0,
  "count_mismatch": false,
  "failed_cases": [ { "case_code": "login", "status": "fail",
                      "attribution": "system_under_test" } ]
} }
```

三条硬规则：

1. **请求体里的 `project_id` 必须等于令牌所属项目**，否则 `40300` ——
   这是"按项目签发"的全部意义，不校验的话按项目签发等于白做；
2. **读结果也要校验项目**，按项目签发要同时管住读；
3. **`exit_code_for_ci` 分三档而不是两档**：把"还在跑"（2）当成"失败"
   会让流水线以为测试挂了，当成"成功"更糟 —— 那是假绿。

**默认异步、同步选配**：CI 里的长连接很容易被网关掐断，让流水线挂在
一个 HTTP 请求上等 20 分钟是脆弱的。`?wait=1` 留给"跑几秒就结束"的场景。


### 2B.1 cron 与时区

- **5 段**（`分 时 日 月 周`），支持 `@daily` / `@every 30m` 等描述符；
- ⭐ **校验在保存时做**（`40000`），不等到调度器启动才失败 ——
  表达式写错是最常见的错误，让它变成一个永远不跑的计划是最坏的结果；
- **每个计划自带 IANA 时区**（默认 `Asia/Shanghai`），`next_fire_at` 按该时区算。
  不绑时区的话，服务器跑在 UTC 上时用户填的「早上 9 点」会是 UTC 9 点 ——
  这类错误不报错，只会静默错位。

### 2B.2 调度语义

一次计划触发 = **为每个用例集各起一条执行记录**
（`RunRecord{ target_type:"suite", trigger_type:"cron", plan_id }`），
而不是合并成一条 `target_type=plan`。理由：用例集之间本就该失败隔离 ——
一个用例集编译失败不该让同计划里的其它用例集也跑不了。

三条硬规则：

1. **重入保护**：上一轮还没跑完就到了下一个调度点 → **跳过**，
   记 `last_skip_reason="上一轮仍在执行"`；
2. **不补跑错过的调度点**，但记 `last_missed_at` —— 静默跳过的定时任务
   不会报错，只会让该跑的没跑；
3. **只在单实例部署下成立**：多实例时每个实例都会触发同一个计划。

**issue.code 字典（M1）**：

> 与 `internal/validator` 的常量逐一对齐。**新增/改名必须同时改这里**，
> 否则前端会拿到一个自己没有分支处理的 code。

| code | level | 含义 | 依据 |
|:---|:---:|:---|:---|
| `UNDEFINED_VARIABLE` | error | 引用了未定义的变量 | 引擎退出码 21 |
| `EMPTY_STEPS` | error | 用例没有任何启用的步骤 | 引擎无"跳过步骤"语法，全部禁用 = 空用例 |
| `MISSING_URL` | error | `request` 步骤缺少 url，或 request 无法解析 | — |
| `MISSING_CASE_NAME` | error | 用例缺少 `config.name` | F11 |
| `INVALID_ASSERT_METHOD` | error | 断言方法不在内置校验器清单内 | `parser.ValidAssertMethods` |
| `INVALID_ASSERT_EXPR` | error | 断言缺少检查表达式（`check`） | — |
| `INVALID_EXTRACT_OBJECT` | error / warning | 提取对象不在 5 类之内（error）；声明了 body/headers/cookies 却没写取值路径（warning） | — |
| `INVALID_EXTRACT_NAME` | error | 提取项没有变量名 | 提取结果无处存放 |
| `INVALID_BODY_TYPE` | error | `body_type` 不在 json / form / raw / none 之内 | — |
| `UNRESOLVED_REF` | error | `step_type=api/testcase` 但引用不存在或已禁用 | 退出码 17 |
| `UNSUPPORTED_STEP_TYPE` | error | `step_type` 在 M1 尚未开放（api / testcase 等） | M1 只支持 request |
| `DUPLICATE_CASE_NAME` | error | `config.name` 与同项目其他用例重复 | F11（summary.json 以用例名作唯一标识） |
| `DUPLICATE_STEP_SEQ` | error | 步骤 `seq` 重复 | seq 决定编译后的书写顺序 |
| `CUSTOM_FUNCTION_UNSUPPORTED` | error / warning | hooks 配置（error）；`${func()}` 非内置函数（warning） | A12 / A13；M1–M4 不支持 `debugtalk.py` |
| `UNKNOWN_FIELD` | error | 渲染后的 YAML 出现引擎不认识的字段 | **A7**：引擎对未知字段完全静默，这是唯一防线 |
| `DUPLICATE_STEP_NAME` | warning | 同名步骤 | 只影响日志可读性 |
| `NO_VALIDATE` | warning | 步骤没有任何断言 | 只能验证"请求发得出去" |
| `PLAINTEXT_SECRET` | warning | 变量值疑似硬编码密钥 | 工程习惯（换环境要改用例） |
| `TRAILING_SLASH_ADDED` | warning | URL 不带查询串，引擎会补结尾斜杠后再发出 | **A1**：`$base_url/get` 实际发出 `GET /get/`。`params: {}` / `params: null` 也照样补，平台无法代改，只能提示 |

### PUT /api/v1/cases/{id}/yaml ⭐ 保存源码（M3 · ③-c）

源码视图里编辑过的 YAML 反解析回结构化并落库。请求体：

```jsonc
{ "yaml": "config:\n    name: ...\n    verify: false\nteststeps:\n    ..." }
```

- 成功：`{ "code": 0, "data": { ...CaseDetail } }`（与 `GET /cases/{id}` 同构）。
- 反解析失败（非法 YAML、字段类型错、缺 `config.name`）：HTTP 200 + `code=50003`，
  `message` 带「第 N 行」前缀，前端据此高亮报错行。

> **语义往返等价**：反解析（`decompiler`）是正向编译（`compiler`）的逆过程，
> 但只还原 YAML 里**表达得了**的内容（name / config / steps）。请求头三层归属、
> verify 来源等 DB 专属信息无法还原，属于「直接编辑编译产物」的固有代价。
> `code` 无法从 YAML 还原（YAML 只有 config.name），沿用原值。

### POST /api/v1/cases/{id}/debug ⭐ 单步调试（M3 · ③-a）

同步执行「前置步骤 + 目标步骤」的临时最小用例，跑完即弃不落库。请求体：

```jsonc
{ "project_id": 1, "case_id": 12, "step_seq": 2, "env_id": 0, "timeout_sec": 0 }
```

- `step_seq`：要调试的目标步骤 seq；平台真实执行「启用的、seq ≤ 它」的前缀步骤，
  以拿到真实变量值（否则依赖 `$token` 的步骤断言必失败）。
- `timeout_sec`：同步阻塞上限，0 = 默认 30s，上限 5 分钟。
- 响应：`{ "code": 0, "data": { status, attribution, steps: [{ seq, name, is_target, extract_result, request, response, assertions }], target_seq, actual_step_count } }`。

> 引擎最小执行单位是**用例文件**（实测 A2），没有「只跑第 N 步」开关，
> 因此平台构造临时最小用例（前置 1..k-1 步 + 目标步 k）跑独立子进程。

### 参数化数据集（M3 · ③-b）

平台层参数化格式：用例 `config.datasets = [{ name, limit }]`（**独立键**，
不是 config.parameters）。编译器渲染时把它转成引擎语法（list → 关联 pairs；
csv → `${P(data/xxx.csv)}`），limit 在编译期裁剪（引擎无 limit 开关，实测 A22）。

| 端点 | 说明 |
|:---|:---|
| `GET /projects/{id}/datasets` | 列表，每项带 `row_count` / `columns` / `limit_effective` |
| `POST /projects/{id}/datasets` | 新建（`name` + `source=list|csv` + `inline` 或 `csv_name`/`csv_text` + `limit`） |
| `GET /datasets/{id}` | 详情 |
| `PUT /datasets/{id}` | 更新 |
| `DELETE /datasets/{id}` | 删除 |
| `GET /datasets/{id}/csv` | 读回 CSV 文本（前端编辑回填） |

- `source=list`：`inline` 存 `[{...}, ...]`，编译时内联成关联 pairs（成对迭代，非笛卡尔积）。
- `source=csv`：CSV 存项目工作区 `data/{name}.csv`，编译时用 `${P(data/{name}.csv)}` 引用；
  `limit>0` 时生成派生文件 `data/{name}__l{N}.csv`（只写前 N 行，编译产物可再生）。
- CSV 写入时校验：至少表头 + 1 行、列数一致、纯文件名（防路径穿越）。
- 引用不存在的数据集：预览/校验时报 `50003`（显式报错，不静默跳过）。

> ⭐ **`rebuilt: true` 是关键契约**：该断言结果不是引擎给出的，而是平台用
> 「用例声明的断言 + stdout 报文快照」自行比对重建的（方案 6.6，因 F8 断言失败时引擎不产出任何明细）。
> 前端必须显式标注「平台重建」，并对 `inferred_failed: true` 的步骤显示为
> 「该步骤未正常结束（引擎在断言阶段崩溃）」—— 见 5.2 的定位规则。

### 5.1 失败步骤定位规则（F8，服务端实现，前端只需展示）

当 `case_result.panic = true` 时，引擎不会给出任何断言明细。服务端按以下顺序重建：

1. 从 stderr JSON 日志中取出**所有** `run step start`（含 `step` 与 `type`）；
2. 取出所有 `run step end`；
3. **有 `start` 但无配对 `end` 的步骤 ⇒ `inferred_failed = true`**，`status = error`；
4. 该步骤的 `request_snapshot` / `response_snapshot` 取 stdout 快照（**完整可用**，因为 panic 发生在请求之后）；
5. `assertions` 由平台按该步骤声明的断言逐条与快照比对，全部标 `rebuilt = true`；
   **第一条不通过的即为失败断言**，其余标注为「未执行到」；
6. 若步骤成功配对（`start` + `end` 且 `success=true`），则 `status = pass`，断言明细取自 stderr 的
   `validate xxx` 日志行。

## 8. 前端必须遵守的硬约束

1. **展示「最终生效 URL」而非 YAML 声明的 URL**（F9）：hrp 在 URL 不带查询串时会自动补尾斜杠，
   `final_url` 字段即为真实请求地址。UI 需在步骤详情中同时展示两者，并给出可能 404 的提示。
2. **HTML 报告可能不存在**（F8）：断言失败必然没有报告，必须处理 `404 / code=50006`。
3. **`rebuilt=true` 的断言不是引擎结论**：需以「平台重建」标注，避免用户误以为引擎给出了该判定。
4. **前端隐藏入口不是权限控制**：非管理员看不到「账号管理」菜单、删除按钮被禁用，
   都只是"不给出点了必然失败的按钮"。真实判定始终在后端（`RequireAdmin`）。
   前端也不得把角色缓存在本地并据此放开任何操作。
5. **`el-table` 的作用域插槽把 `row` 擦成 `DefaultRow`**（一个索引签名对象），
   它和实体类型没有结构关系。别把函数签名放宽成 `any`（等于关掉这些函数的类型检查），
   加一个收窄入口：`function asUser(row: unknown): User { return row as User }`。

## 8A. 统计看板 / 导入 / 导出 / 基线对比（M4）

> 四块都是**只读分析或格式转换**能力，全部复用现有 run_record / case_result /
> step_result 历史，不新增表。聚合刻意放在 Go 内存里做（而非裸 SQL 日期/分组函数），
> 这样 mysql 与 sqlite 两种驱动下行为一致。

### 8A.1 统计看板

| 端点 | 说明 |
|:---|:---|
| `GET /api/v1/stats/trend` | 通过率趋势（按天，含无执行的空白天补零） |
| `GET /api/v1/stats/flaky` | 不稳定/常败用例排行（按 case_code 聚合，通过率升序） |
| `GET /api/v1/stats/slowest` | 慢用例排行（按 case_code 聚合，平均耗时降序） |

查询参数：`project_id`（必填）、`days`（默认 30，上限 365）、`limit`（默认 20，上限 100）。

```json
GET /api/v1/stats/trend?project_id=1&days=7
→ 200 { "code": 0, "data": { "points": [
  { "day": "2026-09-16", "total": 3, "passed": 2, "failed": 1, "error": 0, "rate": 0.667, "avg_ms": 1500 }
] } }
```

`flaky` / `slowest` 返回 `{ "items": [ ... ] }`，元素分别为
`{ case_id, case_code, config_name, runs, passed, rate }` 与
`{ case_id, case_code, config_name, runs, avg_ms, max_ms }`。

> 通过率 = 0（全败）与时好时坏（0<rate<1）都进「需要关注」榜单，
> 全过（rate=1）的健康用例不进；前端按 rate 分档着色。

### 8A.2 导入（HAR / Postman / curl）

| 端点 | 说明 |
|:---|:---|
| `POST /api/v1/projects/{id}/import/preview` | multipart 上传 → 转换预览（不落库） |
| `POST /api/v1/projects/{id}/import/commit` | multipart 上传 → 转换并落库 |

multipart 字段：`file`（必填，≤20MB）、`format`（可选：`auto` / `har` / `postman` / `curl`）。

```json
POST /api/v1/projects/1/import/preview   (multipart/form-data: file=<抓包文件>)
→ 200 { "code": 0, "data": {
  "detected": "har",
  "cases": [ { "name": "...", "code": "...", "module": "...", "step_count": 3, "summary": ["GET /login", ...], "source_file": "..." } ]
} }
```

```json
POST /api/v1/projects/1/import/commit
→ 200 { "code": 0, "data": {
  "created": [ { "id": 101, "code": "...", "name": "..." } ],
  "failed":  [ { "name": "...", "reason": "重名" } ]
} }
```

> 提交**不做整体事务回滚**：逐用例成败都报告，部分失败时改名重导其余的即可。
> name/code 会自动去重（重名追加序号），避免一整个 Postman 集合因一条重名全废。

### 8A.3 导出（项目 → hrp 目录 zip）

| 端点 | 说明 |
|:---|:---|
| `GET /api/v1/projects/{id}/export?env_id=` | 导出项目为 hrp 标准目录结构的 zip |

- **成功**：`200` + `Content-Type: application/zip` + `Content-Disposition: attachment; filename="<code>-export-<时间戳>.zip"`。
- **失败**：统一 JSON 错误（非空 zip）。前端按 Content-Type 区分。
- 导出走 `compiler.Render` 纯渲染（不落盘、只读、永远反映 DB 当前内容），
  单条用例渲染失败**不阻断**整体导出，坏用例写进 zip 内的 README。

### 8A.4 用例基线对比

| 端点 | 说明 |
|:---|:---|
| `GET /api/v1/projects/{id}/baseline?case_id=&limit=` | 选定用例的最近 N 次执行并排对比 |

`project_id` 来自路径，`case_id` 必填（查询串），`limit` 可选（默认 5，上限 30）。

```json
GET /api/v1/projects/1/baseline?case_id=42&limit=5
→ 200 { "code": 0, "data": {
  "case_id": 42, "case_code": "login", "config_name": "登录",
  "total_runs": 12,
  "runs": [   // 从旧到新；第 0 项无 delta
    { "run_id": 801, "run_status": "success", "trigger_type": "manual",
      "finished_at": "2026-09-20T10:00:00+08:00", "status": "pass", "attribution": "pass",
      "duration_ms": 120, "step_total": 2, "step_passed": 2, "step_failed": 0, "step_error": 0, "error_msg": "" },
    { "run_id": 805, "run_status": "failed", "trigger_type": "cron",
      "finished_at": "2026-09-21T10:00:00+08:00", "status": "fail", "attribution": "system_under_test",
      "duration_ms": 320, "step_total": 2, "step_passed": 1, "step_failed": 1, "step_error": 0, "error_msg": "...",
      "delta": { "broke": true, "recovered": false, "dur_delta_ms": 200, "step_pass_delta": -1 } }
  ]
} }
```

`delta` 语义（相邻两次，只做**事实陈述**不下结论）：

- `broke`：前一次通过、这一次失败/出错 —— 典型的最先变坏点；
- `recovered`：前一次失败/出错、这一次通过；
- `dur_delta_ms` / `step_pass_delta`：耗时与通过步骤数的差值（正数 = 变慢/多通过）。

> 基线对比回答「这条用例是从哪一次开始变坏的」，配合统计看板的
> 「不稳定用例」排行一起用：先看板找嫌疑，再进基线确认变坏点。
