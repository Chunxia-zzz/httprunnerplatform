## 一、这个系统是什么

一个基于 **HttpRunner** 引擎的**接口自动化测试平台**。

通俗说：你平时要「写 YAML → 敲 `hrp run` → 去磁盘翻报告」来测接口，这个平台把这些都搬到了
网页上 —— 在页面里点几下就建好用例、执行、看到失败是谁的问题，还能定时自动跑、接进 CI 流水线。

| 项 | 内容 |
|:---|:---|
| 目标用户 | 小型测试团队（约 10 人） |
| 产品形态 | 私有化部署（内网跑，数据不出公司） |
| 交付形态 | 一个可执行文件（前端已内嵌，不用装 Node） + 一个数据库 |

**它帮你解决的三个痛点：**

1. **写用例不用手写 YAML** —— 表单点选即可，断言、变量都能可视化配置。
2. **失败能看出「是谁的问题」** —— 自动区分「被测系统坏了」还是「你用例写错了 / 环境配错了」。
3. **不跑丢、不假绿** —— 执行前后用例数对账，杜绝「用例被静默跳过却显示全绿」。

## 二、底层设计逻辑

### 2.1 执行引擎

- **HttpRunner v4.3.6**（命令行工具 `hrp`）。
- 平台**不 fork、不改引擎源码**，而是把它当作一个外部二进制，**一个用例起一个独立子进程**来调用。
- 为什么必须这样？因为实测发现 `hrp run <目录>` 是「全有或全无」的：一条断言失败会让引擎
  panic（退出码 2），**后续用例全不跑、整批结果丢失**。所以平台强制「一用例一子进程」，单条失败不影响其它用例。

### 2.2 一次「执行」的完整调用链路

```
你点「执行」
   │
   ▼
[编译器 compiler]  把数据库里的用例/环境/变量，渲染成 hrp 能识别的 YAML 工作区文件
   │
   ▼
[执行器 executor]  起一个子进程：hrp run <用例.yaml> --log-json --save-tests --case-timeout N
   │               （工作区目录隔离、可超时、可取消）
   ▼
hrp 引擎实际发 HTTP 请求，产出两路数据：
   ├─ stdout  → 请求/响应报文明细（纯文本）
   ├─ stderr  → 结构化 JSON 日志
   └─ summary.json + HTML 报告（断言失败时引擎 panic，这两者都不会产出）
   │
   ▼
[解析器 parser]   把 stderr JSON + 退出码 + stdout 报文，拼回结构化的步骤级结果
   │
   ▼
[归因 attribution]  判定失败归属：
   │              system_under_test（被测系统问题）/ case_issue（用例问题）/ env_issue（环境问题）
   ▼
落库（run_record + case_result + step_result）→ 前端展示步骤时间线、断言明细、失败归因标签
```

### 2.3 两个关键设计取舍（为什么这么做）

| 取舍 | 原因 |
|:---|:---|
| **一用例一子进程** | `hrp run` 全有或全无，一条失败全挂；隔离后单条失败不影响其它 |
| **关闭引擎遥测** | GA4 + Sentry 默认开启，每次拖 1.3–5.1 秒且上报失败被误判成用例错误；平台注入 `DISABLE_GA/DISABLE_SENTRY` 关掉 |
| **结果自己重建，不全信引擎** | 断言失败时引擎 panic、报告和 summary 都不产出；平台用「声明的断言 + stdout 报文」自己重建失败明细 |
| **用例数对账** | 引擎会静默吞掉畸形用例（退出码 0 假装成功）；平台执行前后对账，防「假绿」 |
| **通知/接口引用/WebSocket 已裁剪** | 数据模型预留了字段，但功能未实现（见 [项目方案 10.2](项目方案.md)）；当前失败告警靠 CI Token + 页面轮询 |

## 三、验收环境准备（先把服务起起来）

> 这一节是**验收前必读**：怎么把后端和前端跑起来、怎么确认就绪、出问题怎么排查。
> 环境参数固化在 `scripts/dev-env.sh` 里，工具链（Go、hrp）装在仓库外的 `F:/httprunnerplatform-tools`。

### 3.0 环境总览

| 进程 | 命令 | 地址 | 说明 |
|:---|:---|:---|:---|
| 后端 | `.smoke/hrpp.exe server -c .smoke/config.yaml` | `http://127.0.0.1:8127` | 冒烟/验收用后端，独立 sqlite 库 `.smoke/smoke.db` |
| 前端 | `HRP_API_TARGET=http://127.0.0.1:8127 npm run dev` | `http://127.0.0.1:5173` | Vue dev server，`/api` 代理到 8127 |

> 两种「跑起来」的方式，**验收推荐方式一（开发模式）**：
>
> - **方式一（开发模式，验收用）**：后端 `hrpp.exe` + 前端 `npm run dev`，改前端即时生效。
> - **方式二（单文件交付模式）**：`bash scripts/build.sh` 产出一个内嵌前端的 exe，
>   浏览器访问 `http://127.0.0.1:8080`。验收看功能用方式一即可。

### 3.1 第一步：载入开发环境（每次新开终端都要做）

```bash
cd /f/httprunnerplatform
source scripts/dev-env.sh
```

这一步会设置好 Go 工具链、国内代理（`goproxy.cn`）、以及 hrp 引擎二进制路径 `HRP_BINARY_PATH`
（`F:/httprunnerplatform-tools/bin/hrp.exe`）。**起服务、跑测试、重新编译都依赖它。**

### 3.2 第二步：起后端

```bash
# 用 Bash 起（别用 PowerShell 起服务）
cd /f/httprunnerplatform
./.smoke/hrpp.exe server -c .smoke/config.yaml
```

确认就绪：

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8127/healthz
# 输出 200 即就绪
```

> 后端数据存在 `.smoke/smoke.db`（sqlite 文件），**不会因为重启丢失**，验收数据隔天还在。

### 3.3 第三步：起前端

```bash
# 在 web/ 目录下，带 HRP_API_TARGET 指向后端（默认代理是 8080，会连不上）
cd /f/httprunnerplatform/web
HRP_API_TARGET=http://127.0.0.1:8127 npm run dev
```

确认就绪：浏览器打开 `http://127.0.0.1:5173`，能看到登录页即可。

### 3.4 常见坑（起不来的原因）

| 症状 | 原因 | 解决 |
|:---|:---|:---|
| 前端能开但登录报 `ECONNREFUSED` | 代理指向了 8080，后端在 8127 | 起前端时加 `HRP_API_TARGET=http://127.0.0.1:8127` |
| 前端起一下就挂 | 用 `npm run dev | head` 之类管道，vite 收到 SIGPIPE 退出 | 直接后台起，别接 `| head` |
| 重新编译后端报 `go: command not found` | 没 `source scripts/dev-env.sh` | 先 `source scripts/dev-env.sh` |
| 端口被占用 | 上次的进程没杀干净 | 用 PowerShell 杀：`Get-Process hrpp -ErrorAction SilentlyContinue \| Stop-Process -Force`；node 同理 |
| 后端报找不到 hrp | `HRP_BINARY_PATH` 没设 | `source scripts/dev-env.sh` |

> **进程管理规范**：杀进程用 PowerShell（`Get-Process ... | Stop-Process`），起服务用 Bash。

## 四、体验流程指引（跟着点一遍）

### 第 0 步：登录

1. 打开浏览器访问 `http://127.0.0.1:5173`（开发模式；单文件交付模式是 `http://127.0.0.1:8080`）。
2. 默认账号：**`admin` / `admin123`**（首次登录后请尽快改密码，右上角「修改密码」）。

### 第 1 步：建一个项目

1. 左侧菜单 → **项目** → 点「新建项目」。
2. 填项目名、项目代码（英文，作为工作区目录名）。
3. 保存后，顶栏会切换到该项目。

### 第 2 步：建一个环境

1. 左侧菜单 → **环境** → 新建。
2. 填 `base_url`（被测服务的根地址，如 `http://127.0.0.1:8080`）、可选全局变量（`$变量名` 形式，渲染成 `.env`）、全局请求头。
3. 保存。环境决定「用例跑向哪个地址、带哪些公共变量」。

### 第 3 步：建第一条用例

1. 左侧菜单 → **用例** → 新建。
2. 起个名字，选模块，然后**添加步骤**：
   - 每个步骤就是一个 HTTP 请求：方法、路径、请求头、参数、请求体。
   - 加**断言**（如「响应 status_code 等于 200」）、**提取**（把响应里的 `token` 存成变量给后续步骤用）。
   - 右侧会实时显示编译后的 YAML，也能直接切到「源码」编辑。
3. 保存。

### 第 4 步：跑一遍，看结果

1. 用例列表里点「**执行**」。
2. 跳转到执行详情：能看到**步骤时间线**（每步耗时）、**断言明细**（哪个断言过了/挂了）、
   **请求/响应报文**、以及最关键的**失败归因标签**——它会告诉你这次失败是「被测系统的问题」还是「用例/环境的问题」。
3. 有失败时，点「HTML 报告」看原始报告（注意：断言失败时引擎不产报告，平台会自己重建失败明细）。

### 第 5 步：调试单个步骤（可选，但很常用）

用例编辑页里，每个步骤有「**调试此步**」按钮。它会只跑「前置步骤 + 这一步」，
不用跑完整流程就能验证请求对不对、变量拿没拿到 —— 点击不超过 3 次。

### 第 6 步：建用例集 + 测试计划（定时自动跑）

1. **用例集**：把多条用例攒成一个集合，拖拽排序（顺序即执行顺序），可设「某条失败后继续还是中止」。
2. **测试计划**：新建计划 = 选一组用例集 + 选环境 + 设触发方式：
   - **手动**：页面点一下就跑。
   - **定时（cron）**：比如「每个工作日 09:00」；平台自带时区（默认 `Asia/Shanghai`），
     并会算出「下一次几点跑」给你看。
3. 保存后，到点自动执行，每次执行在「执行记录」里留痕。

### 第 7 步：接 CI（可选）

1. 左侧菜单 → **CI 令牌**，为项目签发一个 Token（明文只显示一次，记得复制）。
2. 拿到流水线里 curl 调用即可（页面底部给了现成示例），支持 `?wait=1` 同步等结果，
   并用返回的 `exit_code_for_ci`（0/1/2）决定流水线成败。

### 第 8 步：看数据（验收 M4 功能）

- **统计看板**：通过率趋势、不稳定用例排行（时好时坏的重点排查）、慢用例排行。
- **导入**：用例列表「导入用例」，直接传 Postman 集合 / HAR 抓包 / curl 命令，自动转成用例。
- **导出**：项目列表「导出」，把整个项目打包成标准 hrp 目录结构的 zip，可脱离平台用 hrp 命令行跑。
- **基线对比**：用例列表点「对比」，看这条用例最近 N 次执行是怎么从「绿」变「红」的，定位是哪一次开始坏的。

## 五、角色与权限

| 角色 | 能做什么 |
|:---|:---|
| `admin` 管理员 | 建账号、删项目、所有功能 |
| `member` 成员 | 建用例/用例集/计划、执行、看结果；看不到「账号管理」入口 |

## 六、常见疑问（FAQ）

**Q：为什么有的用例明明跑完了，页面却显示「假绿」告警？**
A：这是平台在保护你——引擎可能静默吞掉了畸形用例（退出码 0 假装成功）。平台对账发现
「该跑的用例数 ≠ 实际跑的」，会强制标成 error，提醒你别被「全绿」骗了。

**Q：断言失败了为什么看不到 HTML 报告？**
A：HttpRunner v4.3.6 的已知缺陷：断言失败会让引擎 panic，报告和 summary.json 都不产出。
平台会用自己的「声明断言 + 响应报文」重建失败明细，所以页面上的步骤级失败原因依然是准的。

**Q：能不能用 Python 自定义函数（`debugtalk.py`）？**
A：暂不支持。实测它需要全局 venv + PyPI 网络，且插件路径可能无限挂起（引擎无超时保护）。
十人团队的接口用例绝大多数用不上；确有需要（如签名计算）可用内置变量函数替代。

**Q：通知（企微/钉钉/Webhook）为什么没有？**
A：这是 M2 的裁剪项，数据模型预留了字段但发送器未实现。当前失败告警靠「CI Token + 流水线结果」或页面轮询。
