## 2. 逐项实测详录

### 2.1 ① `--log-json` 的真实字段结构

**命令**

```bash
cd testdata/minimal && hrp run testcases/a_pass.yml --log-json 1>stdout.txt 2>stderr.txt
```

**结论：存在两条完全不同的流，必须同时采集、分别解析。**

#### stderr —— 引擎日志，JSON Lines（zerolog）

每行一个独立 JSON 对象，可逐行 `json.Unmarshal`。已观测到的字段全集：

| 类别 | 字段 |
|:---|:---|
| 通用 | `level`（info/warn/error）、`time`（`2026-09-22T17:28:41.493+0800`，本地时区带偏移）、`message` |
| 初始化 | `log_level`、`failfast`、`saveTests`、`timeout_seconds`、`hrp_version` |
| 加载 | `path`、`key`、`count` |
| 执行 | `testcase`、`step`、`type`（如 `request-GET`）、`success`、`elapsed(ms)`、`exportVars`（无导出时为 `null`） |
| 断言 | `checkExpr`、`assertMethod`、`expectValue`、`expectValueType`、`checkValue`、`checkValueType`、`result` |
| 错误 | `error` |
| 插件 | `output`、`plugin`、`functionNames`、`packages` |

观测到的 `message` 取值（可作为状态机的事件名）：

```
log with json output / set global log level
[init] SetFailfast / SetSaveTests / SetCaseTimeout / SetRequestsLogOn
start running / load file / set env / load testcases successfully
reset session runner
run testcase start / run testcase end
run step start / run step end
validate status_code
locate plugin failed              ← warn，每个用例一条，见 A3
start to prepare python plugin / find all function names
generate debugtalk success / build python plugin successfully
python3 venv is not ready
[Run] init case runner failed
```

> ⚠️ **`run step start` / `validate xxx` / `run step end` 三件套是「通过」的判据。**
> **断言失败时，`validate` 与 `run step end` 都不会出现** —— stderr 停在 `run step start` 后直接跟 panic（见 2.3）。

#### stdout —— 请求/响应明细，纯文本（非 JSON）

可用 `--log-requests-off` 关闭。每步一个区块，分隔符为**固定长度字符行**：

| 行 | 内容 | 长度 |
|:---|:---|:---:|
| 步首 | `-------------------- request --------------------` | 49 字符 |
| | 请求行 `GET /get/ HTTP/1.1` + 头 + 空行 + body | |
| 响应首 | `==================== response ====================` | 50 字符 |
| | `Connected via plaintext`（传输层信息） | |
| | 状态行 + 响应头 + 空行 + body | |
| 步尾 | `--------------------------------------------------`（50 个 `-`） | 50 字符 |

**请求失败时**：只打印 `request` 区块，**没有 `response` 区块，也没有步尾分隔线**，随后接 `hrp exit N`。

**实例（成功步）：**

```
-------------------- request --------------------
GET /get/ HTTP/1.1
Host: 127.0.0.1:8899


==================== response ====================
Connected via plaintext
HTTP/1.1 200 OK
Content-Length: 197
Content-Type: application/json; charset=utf-8
Date: Tue, 22 Sep 2026 09:36:23 GMT
Server: LocalEcho/1.0 Python/3.13.14

{"args": {}, "headers": {...}, "method": "GET", "path": "/get/", ...}
--------------------------------------------------
```

#### `hrp exit N` 的位置 —— 意外的二级判别器

`hrp exit N` **打印在 stdout**（不是 stderr）。

> ⚠️ **本节结论已在 M1 开发期修正**（详见第 8 节 A16）。
> 本文档初版写的是「只在进程正常退出时出现」，**这是错的**。
> 取得官方源码后确认真实规则是：**只在退出码非 0 时出现**。
>
> ```go
> // hrp/internal/code/code.go
> func GetErrorCode(err error) (errCode int) {
>     if err == nil {
>         return Success          // ← 提前 return，跳过了下面的打印
>     }
>     ...
>     fmt.Printf("hrp exit %d\n", errCode)
>     return
> }
> ```
>
> 因此 **exit=0 时没有 `hrp exit 0`**。实测复核：`pass_2steps` / `pass_extract`
> 两个成功夹具的 stdout 末尾确实没有这一行，而 exit=1/21/23 的夹具都有。

| 退出码 | 场景 | 实测 stdout 是否有 `hrp exit N` |
|:---:|:---|:---:|
| 0 | 全部通过 | ❌ **没有**（`GetErrorCode` 提前 return） |
| 1 | 请求失败 / 请求超时 | ✅ 有（`hrp exit 1`） |
| 9 | Python venv 未就绪 | ✅ 有 |
| 21 | 变量未定义 | ✅ 有 |
| 23 | hook 函数不存在 | ✅ 有 |
| **2** | **断言失败 → panic** | ❌ **完全没有**（进程崩溃，走不到打印） |

> **正确用法**：`hrp exit N` 的作用是「印证进程是**主动退出并给出了明确错误码**的」，
> 与 `exitCode == 0` 一起构成「是否被 panic 或强杀打断」的判据：
>
> ```
> CleanExit = (exitCode == 0) || stdout 含 hrp exit N
> ```
>
> 它**不能**用来判断"是否成功" —— 成功时恰恰没有这一行。

### 2.2 ② HTML 报告的真实落盘位置

**命令**

```bash
cd testdata/minimal && hrp run testcases/a_pass.yml --gen-html-report --log-json
```

**产物**

```
testdata/minimal/results/20260922172751/report.html     17,531 字节
```

**结论**

1. 路径为 **`<项目根>/results/<YYYYMMDDHHMMSS>/report.html`** —— 印证源码 `hrp/internal/env/env.go` 的 `results/{timestamp}/`；
   **官方文档写的 `reports/report-<时间戳>.html` 是错的**（目录名 `reports` vs `results`，文件名也不含 `report-` 前缀）。
2. **完全自包含的单文件 HTML**：无 `<script src>`、无外部 `<link href>`（仅页内锚点 `#record_x_y` / `#popup_log_x_y`）。
   → 平台**直接托管/内嵌这一个文件即可，无需映射静态资源目录**。
3. 结构：`<h1>API Test Report</h1>` + `Summary` + `Details` + `Request and Response data` 四段；通过记录用 `class="passed"`。
4. `--gen-html-report` 与 `--save-tests` **可以同跑**，产物落在**同一个时间戳目录**下：

```
results/20260922173020/report.html
results/20260922173020/summary.json
```

**⚠️ 时间戳精度只到「秒」** —— 同一项目根下同一秒内启动的两次运行会**复用同一目录**（互相覆盖）。
→ **平台必须为每次执行分配独立工作区**（方案 6.2 已要求），否则并发执行必然串台。

### 2.3 ③ 断言失败退出码 —— 颠覆性修正

**命令**

```bash
cd testdata/assert-probe
hrp run cases/a_status.yml -s --log-json    # 期望 201，实际 200
```

**结果：`EXIT=2`，并产生 Go panic，且 `results/` 目录完全没有被创建。**

#### 四类断言失败全部同构

| 用例 | 断言内容 | 退出码 | panic 行数 | `results/` 产物 |
|:---|:---|:---:|:---:|:---|
| `a_status.yml` | `eq: ["status_code", 201]`（实际 200） | **2** | 2 | **无** |
| `b_bodypath.yml` | `eq: ["body.no_such_key.deep", "x"]` | **2** | 2 | **无** |
| `c_header.yml` | `eq: ["headers.X-No-Such-Header", "x"]` | **2** | 2 | **无** |
| `d_second_fails.yml` | 第 1 步通过，第 2 步 status 不匹配 | **2** | 2 | **无** |

→ **不是「body 路径不存在」这种特例才 panic，而是「任何断言失败」都 panic。**

#### 根因（栈回溯，可直接定位源码行）

```
panic: runtime error: invalid memory address or nil pointer dereference [recovered]
  main.main.func1()                          /github/workspace/hrp/cmd/cli/main.go:20
  testing.(*common).decorate(...)            /usr/local/go/src/testing/testing.go:772
  testing.(*common).logDepth(...)            /usr/local/go/src/testing/testing.go:1035
  testing.(*common).Errorf(...)              /usr/local/go/src/testing/testing.go:1068
  testify/assert.Fail(...)                   .../testify@v1.8.4/assert/assertions.go:333
  testify/assert.EqualValues(...)            .../testify@v1.8.4/assert/assertions.go:538
  hrp/internal/builtin.EqualValues(...)      /github/workspace/hrp/internal/builtin/assertion.go:53
  hrp.(*responseObject).Validate(...)        /github/workspace/hrp/response.go:198
  hrp.runStepRequest(...)                    /github/workspace/hrp/step_request.go:431
```

**机制**：`builtin/assertion.go:53` 把**未初始化的 `*testing.common`** 传给 `testify`。

- 断言**通过**时：testify 直接返回，不触碰 `common` → **无异常**；
- 断言**失败**时：testify 调 `Fail()` → `Errorf()` → `common.logDepth()` → `common.decorate()` → **空指针 → panic**。

**因此 `hrp v4.3.6` 在能力上无法报告任何断言失败 —— 它只会崩溃。**

#### 与官方退出码表的冲突

`hrp/internal/code/code.go` 的区间设计是 `0/1` → `[2,10)` 环境 → …
官方表里 **`1 = GeneralFail`** 被顺理成章地理解成「断言失败」。

**实测否定这一理解**：

| 场景 | 退出码 | panic | summary.json | 实际语义 |
|:---|:---:|:---:|:---:|:---|
| 连接被拒（`127.0.0.1:9999`） | **1** | 无 | ✅ **正常产出** | **请求/环境失败**（`do request failed: Get "..."`） |
| 断言不通过 | **2** | **有** | ❌ **完全不产出** | **断言失败（被 panic 顶掉）** |

> **正确表述：`1` = 用例没跑完（环境/网络/服务不可用）；`2` = 用例跑完了但断言不通过。**
> 而 `2` 之所以落到「环境」区间，纯粹是因为 **Go runtime 未捕获 panic 的固定退出码就是 2**，属于巧合，不是设计。

#### 失败运行时可以拿到什么（平台必须据此设计）

`a_status.yml` 失败时的**全部**信息：

**stderr（最后 2 行 JSON + panic 文本）**

```json
{"level":"info","testcase":"ASSERT-status-mismatch","message":"run testcase start"}
{"level":"info","step":"status_code expects 201 but server returns 200","type":"request-GET","message":"run step start"}
panic: runtime error: invalid memory address or nil pointer dereference [recovered]
...（约 40 行 Go 栈）...
```

**stdout（请求/响应快照完整保留 —— 15 行）**

```
-------------------- request --------------------
GET /get/ HTTP/1.1
Host: 127.0.0.1:8899


==================== response ====================
Connected via plaintext
HTTP/1.1 200 OK
...
{"args": {}, ...}
--------------------------------------------------
```

**关键推论**：panic 发生在 **HTTP 请求已完成之后、断言求值期间**。
所以 → **请求/响应快照是完整的，但「哪个断言失败、期望值/实际值」的机器可读记录为零。**

### 2.4 ④ 目录输入的发现与执行顺序

**命令**

```bash
cd testdata/order-test && hrp run cases/ --log-json
```

目录内容与观测顺序：

```
cases/01_first.yml       → ORDER-01_first
cases/02_second.yml      → ORDER-02_second
cases/10_tenth.yml       → ORDER-10_tenth
cases/Z_upper.yml        → ORDER-Z_upper        ← 大写排在小写之前
cases/a_alpha.yml        → ORDER-a_alpha
cases/subdir/inner.yml   → ORDER-SUBDIR-inner   ← 递归进子目录
```

**结论**

1. **顺序 = 字节序（ASCII）字典序**，逐层排序、深度优先递归。
   证据：`Z_upper`（`Z`=0x5A）排在 `a_alpha`（`a`=0x61）**之前**。
   → **不是自然排序**（自然排序会得到 `a_alpha` 在 `Z_upper` 前）。
2. **递归子目录**，无深度限制迹象。
3. **扩展名白名单**（实测）：`.yml` ✅、`.yaml` ✅、`.json` ✅、`.txt` ❌（stderr 中**连 `load file` 都没有**，说明在遍历阶段就被过滤，不是加载阶段失败）。

> **平台含义**：用例执行顺序**可直接由文件名前缀控制**（`01_`、`02_`…）。
> 平台生成的用例文件名建议统一加零填充序号前缀，把顺序显式化，不要依赖用户命名习惯。

#### ⭐ F5「假绿」实证

`ext-probe/cases/` 放入 4 个可发现文件，其中 1 个是畸形 YAML：

| 文件 | 遍历时尝试加载 | 实际执行 |
|:---|:---:|:---:|
| `broken.yml`（畸形 YAML） | ✅ 有 `load file` 日志 | ❌ **静默丢弃** |
| `ok.yml` | ✅ | ✅ |
| `ok2.yaml` | ✅ | ✅ |
| `ok3.json` | ✅ | ✅ |
| `sneaky.txt` | ❌ 未尝试 | ❌ |

**本次运行结果：`EXIT=0`、`stat` 显示 3 条全部通过、无任何 error 日志。**

stderr 中与 `broken.yml` 相关的行**只有一条 `load file`**，**没有任何 warn / error 指出它被跳过**。
（唯一的 3 条 warn 是 `locate plugin failed`，每个成功用例一条，与本问题无关。）

> **F5 从「源码推断」升级为「实测坐实」：**
> **畸形用例文件被完全静默地丢弃 —— 不执行、不报错、不告警、退出码 0。**
> 若不做事前校验 + 事后用例数对账，平台会在「少跑了用例」的情况下向用户展示**全绿**。

```jsonc
            ]
          },
          "content_size": 197
        }
      ],
      "root_dir": ""                           // ⚠️ 恒为空字符串
    }
  ]
}
```

**三条必须记住的结论**

1. **`details[].root_dir` 恒为 `""`，且 `details[]` / `records[]` 中没有任何源文件路径字段。**
   → 单进程跑一个目录时，**无法把结果回填到具体的用例文件**。唯一可靠的对应方式是**依赖执行顺序**（④ 已确认是确定性字典序），这非常脆弱。
   → **结论：平台必须「一个用例 = 一个子进程」**，用进程边界做天然归属。见 A2。
2. **`name` 取的是 `config.name`**，不是文件名。**两条不同的用例若 `config.name` 相同，结果无法区分** → 平台编译期应强制 `config.name` 唯一（可用用例 ID + 名称拼装）。
3. **产出条件受限**：正常退出才有 summary.json。

| 场景 | 退出码 | summary.json |
|:---|:---:|:---|
| 全部通过 | 0 | ✅ |
| 请求失败（连接被拒） | 1 | ✅（`success:false`，`stat` 与 `records` 均正确标失败） |
| **断言失败** | **2** | ❌ **完全没有** |
| Python 插件失败 | 9 | ❌ |

> 即：**唯一没有结构化结果的失败类型，恰恰是最常见的「断言不通过」。**

### 2.6 ⑥ `debugtalk.py` 与 Python venv

#### 情形 A：项目中没有 `debugtalk.py` —— 零开销 ✅

`testdata/minimal`、`order-test`、`ext-probe`、`batch-probe`、`assert-probe`、`slash-probe` 六个工程**均无 `debugtalk.py`**，全部运行正常。
stderr 中**完全没有**准备 venv 的任何步骤，**不探测 python、不装包**。

> **这是平台的关键设计依据：只要不引入 `debugtalk.py`，Python 依赖链可以被完全绕开。**

#### 情形 B：项目中有 `debugtalk.py` —— 完整流程与实测耗时

在 `testdata/plugin-test/debugtalk.py` 中定义两个函数（`add` / `stamp`），用例用 `${add(1, 2)}` 调用。

**实测（冷启动）：`EXIT=9`，总耗时 7,103 ms。**

时间线（stderr 时间戳还原）：

| 时刻 | 事件 | 累计 |
|:---|:---|:---|
| `.391` | 进程启动 | 0 ms |
| `.395` | `start to prepare python plugin`（`path`→`output`） | 4 ms |
| `13.195` | `find all function names` → `functionNames:["add","stamp"]` | **+800 ms** |
| `13.197` | `generate debugtalk success` + `build python plugin successfully` | +802 ms |
| — | `ensure python3 venv: python3=C:\Users\Administrator\.hrp\venv\Scripts\python.exe packages=["funppy"]` | — |
| `18.622` | ❌ `python3 venv is not ready`：`pip install funppy failed` | **+5,428 ms** |

**关键事实**

1. **venv 是全局共享的，不是项目级**：`C:\Users\Administrator\.hrp\venv`（即 `~/.hrp/venv`）。
   → 平台**无法为每个项目做隔离**；多项目共用同一 venv 与同一套包版本。
2. **`funppy` 是重依赖**：实测依赖链 `funppy 0.5.2` → `grpcio` + `grpcio-tools` + `protobuf` + `setuptools`，是数十 MB 级 wheel 安装。
3. **hrp 会通过 `cmd.exe` 拉起子进程**（`[INFO] fungo: exec command: cmd=C:\Windows\system32\cmd.exe`）。
4. **hrp 在项目根目录写文件**：`.debugtalk_gen.py`（291 字节，自动生成，`DO NOT EDIT`）+ `__pycache__/`。
   → 若平台把 hrp 指向用户受 Git 管理的用例仓库，会**污染工作区**。
5. **本机 funppy 实际已安装**（手动 `pip install funppy` 报 `Requirement already satisfied: funppy in ... (0.5.2)`），
   但 hrp 仍判定「not found」并尝试安装、然后失败 → **hrp 的包探测/安装逻辑对本机环境不适用**。
6. **⭐ 更糟：插件路径会无限挂起。** 显式传 `--venv "C:/Users/Administrator/.hrp/venv"` 重试，
   进程运行 **2 分 1 秒仍未退出**（外层 `timeout 90` 对 Windows 子进程不生效），最终只能人工终止。
   → **hrp 自身没有任何超时保护**，插件路径卡住就是永久卡住。

**.debugtalk_gen.py 产物（节选）**


> ② 引入后平台要额外承担全局 venv 运维 + 网络可达 PyPI + 无限挂起的进程管理；
> ③ 若确有需要（如签名计算），可用「平台内置 Go 侧变量函数」替代，或作为后期独立里程碑（并强制预置 venv + 强制超时）。

## 3. 实测副产物：6 条额外关键事实（A1–A6）

### A1 ⭐ URL 尾斜杠自动归一化

| 用例声明的 url | 是否带查询串 | hrp 最终请求的 URL | 服务端收到的 path |
|:---|:---:|:---|:---|
| `$base_url/get` | 否 | `http://127.0.0.1:8899/get/` | `/get/` |
| `$base_url/anything/abc` | 否 | `.../anything/abc/` | `/anything/abc/` |
| `$base_url/anything` | 否 | `.../anything/` | `/anything/` |
| `$base_url/anything/abc/` | 否 | `.../anything/abc/` | `/anything/abc/` |
| `$base_url/anything/abc?inline=1` | **是**（inline） | `.../anything/abc?inline=1` | `/anything/abc` |
| `$base_url/anything/abc` + `params: {k: v}` | **是**（params） | `.../anything/abc?k=v` | `/anything/abc` |
| `$base_url/anything/abc/` + `params: {k: v}` | **是**（params） | `.../anything/abc/?k=v` | `/anything/abc/` |
| `$base_url/get` + `params: {}`（空对象） | 否 | `.../get/` | `/get/` |
| `$base_url/get` + `params:`（null） | 否 | `.../get/` | `/get/` |
| POST `$base_url/anything/xyz` + body | 否 | `.../anything/xyz/` | `/anything/xyz/` |

**规则：最终 URL 不携带查询串时，hrp 会给路径补一个 `/`；一旦有查询串（inline 或 `params:`）则不补，原路径原样保留。与 HTTP 方法、是否带 body 无关。**

⚠️ **补充实测（M1 开发期）**：后两行是本次补测的，结论很关键 ——
**`params: {}`（空对象）和 `params: null` 都**不会**产生查询串，因此照样被补斜杠。**
这堵死了"用空 `params` 块骗过引擎"这条退路：**唯一的规避写法是补一个真实存在的
查询串**（或让 URL 本身以 `/` 结尾，此时补不补都一样）。

**影响**：Spring Boot（默认不做尾斜杠匹配）、Django、部分 API 网关对 `/api/users/` 与 `/api/users` 的行为不同（404 或 301）。
→ **平台在调试视图/报告里必须展示「最终生效 URL」（取自 summary.json `req_resps.request.url`），而不是 YAML 里写的 URL**；
→ 用例编辑器应给出提示或提供「禁止自动补斜杠」的规避写法（补查询串）。

**✅ 平台落地状态（M1）**：上面这条"编辑器应给出提示"已实现 ——
`internal/validator` 的 `TRAILING_SLASH_ADDED`（**warning** 级，不阻断保存与执行），
触发条件是「URL 无 `?`、不以 `/` 结尾、且 `params` 为空」。
不用 error 级是因为绝大多数服务对结尾斜杠不敏感，做成 error 会挡住大量正常用例。
在页面上的实际价值：M1 端到端冒烟里那条"本该通过的用例"正是栽在这里
（`url: $base_url/get` → 实际发出 `GET /get/` → mock 返回 404 → 断言失败 → 引擎 panic），
而当时校验器一个字都没提示。

### A2 ⭐⭐ 批量失败传染 —— 决定平台执行架构

`testdata/batch-probe/cases/`：`1_pass.yml` → `2_fail.yml` → `3_pass.yml`

```
$ hrp run cases/ -s --log-json
EXIT=2
实际执行到的用例:  BATCH-1-pass ✅ → BATCH-2-fail 💥(panic) → BATCH-3-pass ❌ 从未执行
results/ 产物:     (无任何产物 —— 连第 1 条通过的用例的结果也没落盘)
```

**`hrp run <目录>` 是「全有或全无」的：**

- 任何一个用例断言失败 → panic → **进程死亡**；
- **后续用例根本不执行**（`--continue-on-failure` 在 panic 面前无效）；
- **该批次的全部结构化结果丢失**，包括此前已通过的用例。

> **平台硬性约束：执行器必须「一个用例 = 一个独立子进程」。**
> 这同时解决了 ⑤ 中「结果无法回填到用例文件」的问题 —— 进程边界即归属边界。
> 代价是进程启动开销（实测单次冷启动约 0.9 s，属可接受范围），换来的是**故障隔离与结果确定性**。

### A3 `locate plugin failed` 是常驻噪音

**每个用例、每次执行都会产生一条** `{"level":"warn","path":"cases\\ok.yml","message":"locate plugin failed"}`，
**即使项目里完全没有 `debugtalk.py`、没有任何自定义函数**。

→ **日志解析器绝对不能把 `level=warn` 当作异常信号**；
→ 平台的「执行日志」视图应把这条**默认折叠/过滤**，否则用户天天看到红黄告警而实际一切正常。

### A4 退出码 1 的失败会被完整记录

连接被拒场景（`http://127.0.0.1:9999`）实测 summary.json：

```json
{ "success": false,
  "stat": { "testcases": {"total":1,"success":0,"fail":1},
            "teststeps": {"total":1,"successes":0,"failures":1} },
  "details": [ { "name": "ENV-connection-refused", "success": false,
                 "records": [ { "name": "connect to a port with nothing listening",
                                "success": false, "step_type": "request" } ] } ] }
```

`error` 消息为 `do request failed: Get "http://127.0.0.1:9999/get/": dial tcp 127.0.0.1:9999: connectex: No connection could be made...`

→ **「请求/环境失败」这一类反而记录得最完整**（summary.json + 明确的 `error` 文案）。
平台可据此给出高质量提示：「目标服务未启动或网络不可达」，而不是含糊的「执行失败」。

### A5 hrp 会往项目根目录写入产物

一次执行可能产生：`results/`、`.debugtalk_gen.py`、`__pycache__/`。

→ 独立工作区（方案 6.2）是**必须**的，不能直接对用户用例目录执行；
→ 平台生成的脚手架工作区应在 `.gitignore` 中排除 `results/`、`__pycache__/`、`.debugtalk_gen.py`。

### A6 hrp 无自带超时保护（Python 插件路径）

`--case-timeout`（默认 3600）只管**单个用例的执行时长**，**不覆盖插件准备阶段**。
实测插件路径可无限挂起（>2 分钟无任何输出、无退出）。

→ 平台必须在**进程组级别**实现超时与强杀，不能依赖 `--case-timeout`，也不能依赖 shell 的 `timeout`；
→ Windows 下 `timeout` 命令**不会杀掉 hrp 派生出的 `cmd.exe`/`python.exe`**，必须用 Job Object 或按进程树杀。

| # | 约束 | 来源 | 落地方式 |
|:--|:---|:---|:---|
| C1 | **必须同时采集 stdout 与 stderr 并分别解析** | ① | `cmd.Stdout` / `cmd.Stderr` 各自接管道；stderr 按 JSON Lines 流式解析，stdout 按分隔符分块解析 |
| C2 | **必须一个用例一个子进程** | A2 | 执行器循环调用 `hrp run <单个文件>`；结果归属由进程边界保证 |
| C3 | **不能依赖退出码做归因，必须结合 panic 标记** | ③ A15 | 判别顺序：平台取消/超时 → `exit=0` → **stderr 含 `panic:`** → `exit=1` 按错误文本分流 → 其余按 A15 的逐码表。**`exit=2` 且无 panic 归 `unknown`，不猜** |

| C5 | **必须做事前静态校验 + 事后用例数对账** | ④(F5) **A7** | 编译期校验 + 执行后 `expected_case_count` vs `actual_case_count`，不一致标 `error`。**A7 让事前校验从"加分项"变成"必需项"** |
| C6 | **必须给每次执行分配独立工作区** | ②(A5) | 时间戳精度仅到秒 + 产物写项目根 → 不隔离必然串台 |
| C7 | **必须实现进程树级别的超时与取消** | A6 | 不要用 `--case-timeout` 当超时；Windows 需 Job Object / 进程树杀 |
| C8 | **`config.name` 必须强制唯一** | ⑤ | summary.json 用 `config.name` 作唯一标识，重名则结果不可区分 |
| C9 | **调试与报告必须展示「最终生效 URL」** | A1 | 取自 summary.json / stdout 快照，而非 YAML 原文 |
| C10 | **不得把 `level=warn` 当告警** | A3 | `locate plugin failed` 是常驻噪音，需白名单过滤 |
| C11 | **用例文件名加序号前缀以显式控制顺序** | ④ | 顺序为 ASCII 字典序，编译期按元数据顺序生成文件名 |
| C12 | **M1–M4 不支持 `debugtalk.py`** | ⑥ | 绕开 Python/venv/funppy 全链路 |
| **C13** | **必须自建 YAML 字段白名单校验** | **A7** | 引擎对未知字段**完全静默**，不做任何校验。拼错字段名或放错层级都不会报错，只会"配了不生效"。用户唯一能依赖的防线就是平台的事前校验 |
| **C14** | **`timeout` 只能渲染到 `request` 层** | A8 A10 | `teststep.timeout` 静默忽略；平台若要做步骤级超时，只能写进 `request.timeout` |

| **C16** | **步骤状态判据：有 `run step end` 的失败 ≠ 断言失败** | A16 | 断言失败会 panic，走不到 `run step end`。因此"带 end 且 success=false" ⇒ `error`（步骤没跑完）；"无 end" ⇒ `fail`（被测行为不符预期） |
| **C17** | **`CleanExit` 必须包含 `exitCode == 0` 这一支** | A14 | `hrp exit N` 只在 N≠0 时打印，单靠它会把成功误判成异常退出 |
| **C18** | **`hrp exit N` 必须当作 stdout 报文块的终止符** | A18 | 否则请求失败时它会混进请求体，用户在页面上看到"请求体 = hrp exit 1" |
| **C19** | **失败步骤的错误文本取自 summary.json 的 `attachments`** | A17 | 失败记录**没有 `data` 段**，错误文本只在顶层 `attachments`；不取则失败只剩 `success=false` 而无原因 |
| **C20** | **"URL 无查询串" 这个坑无法靠改写 YAML 绕开，只能靠校验提示** | **A1 补充** | `params: {}` 与 `params: null` 实测**照样被补斜杠**，所以平台无法在编译期"替用户修好"。唯一做得到的是事前给出 `TRAILING_SLASH_ADDED`（**warning** 级）提示，让用户自己决定是补查询串还是改用例 |
| **C21** | **必须显式关闭引擎遥测（GA4 + Sentry）** | **A20** | 通过子进程环境变量 `DISABLE_GA=true` / `DISABLE_SENTRY=true`（无 CLI 参数；值必须是字面量 `"true"`；必须在进程启动前设好）。不关的代价：耗时随外网可达性在 1.3–5.1 秒间跳动（GA4 超时 5 秒），且上报失败用 `log.Error()` 打出，会被当成用例错误挂到成功执行上 |

## 5. 对《项目方案》的修正清单

| 位置 | 原文 | 修正为 |
|:---|:---|:---|
| 3.4 **F1** | 「日志写 stderr，不是 stdout；stdout 只有 `code.GetErrorCode()` 里的 `fmt.Printf`」 | 日志确实在 stderr ✅；但 **stdout 并非只有 `hrp exit N`** —— **请求/响应明细（纯文本，约 15 行/步）也打在 stdout**，且可用 `--log-requests-off` 关闭。**`hrp exit N` 只在正常退出时出现，panic 退出时没有** |
| 3.4 **F5** | 源码推断「坏文件静默吞掉」 | 已**实测坐实**：4 个可发现文件中 1 个畸形，静默丢弃、零 warn/error、**退出码 0**、summary 显示 3/3 全通过 |
| 6.3 归因表 | 「**1** = GeneralFail = 🔴 断言未通过 = 被测系统」 | **完全相反**：**`1` = 请求/环境失败**（且 summary.json 正常产出）；**`2` = 断言失败**（Go panic，且 summary.json 完全不产出） |
| 6.3 核心洞察 | 「退出码 1 = 断言不过；10–24 = 用例没跑起来；两个区间完全不重叠，是有意设计的稳定契约」 | 需改写：`1` 是**请求未完成**；**断言失败落在 `2`**，且原因是 **Go panic 的固定退出码**（非设计契约）。「契约」说法不成立 |
| 6.3 实现要点 | 「以进程退出码为准，stdout 文本作为兜底校验」 | 退出码**不足以单独归因**（断言失败与环境共享 `2`？实测环境失败为 `1`，但 panic 也占 `2`）。**必须以「stderr 是否含 `panic:`」为主判别器** |
| 6.5 L2 数据源 | 「`--save-tests` 的 summary」列为备选 | 升格为**主数据源之一**，但须注明**断言失败时完全不产出**，必须在执行器里对「无 summary.json」做显式分支 |
| 6.5 L3 兜底 | 「进程退出码 + 原始日志原文」 | 增加 **stdout 请求/响应快照解析**（断言失败时唯一可用的明细） |
| 6.5 解析器要求 | 「容忍非 JSON 行」 | 明确：stderr 尾部可能是**数百行 Go 栈回溯**；解析器**必须按行 try-parse，失败即丢弃**，且**保留原文** |
| 6.2 隔离 | 「不隔离必然串台」 | 补强依据：**时间戳精度仅到秒**，同秒并发会落到同一 `results/<ts>/` |

## 8. 第二轮实测（A7–A17）：字段语义 / 超时 / 钩子 / 退出码表

**背景**：M1 开发到编译器与解析器时需要确定三件事 —— YAML 里哪些字段在哪个层级生效、
超时该怎么配、退出码到底怎么映射。这些都是"文档没写清、只能实测"的问题，
于是补做了这一轮。**其中 A7 / A13 / A14 直接改变了实现。**

### A7 ⭐⭐⭐ 引擎对未知字段完全静默忽略

**探针**：`testdata/field-probe/cases/f5_unknown.yml`，在 config、request 两层各塞一个不存在的键。

```yaml
config:
    name: "FIELD-unknown-key"
    this_key_does_not_exist: 123
teststeps:
    -
        name: "request with bogus field"
        request:
            method: GET
            url: $base_url/get
            bogus_field_xyz: "hello"
```

**结果**：`exit=1`（连接失败，因为目标是 9999 端口），但**全程零 warn、零 error、
没有任何 `unknown field` 之类的提示**。引擎照常加载、照常执行。

**结论**：**hrp 不做任何 YAML schema 校验**，未知字段连警告都没有。

**对平台的影响（这是 C13，也是新的一条硬约束）**：

| 后果 | 平台必须做什么 |
|:---|:---|
| 字段名拼错（`urls` / `statuc_code`）→ 静默失效 | **校验器必须自建字段白名单**，把"引擎不认识的键"在保存/执行前拦下来 |
| 字段放错层级（见 A14/A15）→ 静默失效 | 编译器必须逐字段对齐实测结论，不能靠"看起来合理"推断 |
| 前端提交了引擎不支持的字段 → 用户以为配了 | 白名单校验是**唯一**的防线，引擎不会兜底 |

> 这条事实把「事前静态校验」从"锦上添花"提升为**架构必需**：
> 引擎不报错，平台不校验，用户就永远不知道自己配的东西没生效。

### A8 ⭐ `request.timeout` 生效，且**触发时退出码是 1**

**探针**：`testdata/timeout-probe/cases/t1_request.yml`

```yaml
teststeps:
    -
        name: "request timeout 1s against delay 6s"
        request:
            method: GET
            url: $base_url/delay/6?x=1      # 注意 ?x=1，见下方"踩坑"
            timeout: 1
        validate:
            - eq: ["status_code", 200]
```

**结果**

```
exit=1  wall=2947ms
```

对照组的启动开销约 1.45 s，因此请求实际在 ~1.5 s 处被中断 → **超时生效**。

**错误文本**（逐字）：

```
do request failed: Get "http://127.0.0.1:8899/delay/6?x=1": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

> **踩坑记录**：第一次探针写的是 `url: $base_url/delay/3`，结果 3 秒的延迟只跑了 1 秒。
> 原因是 **A1 的尾斜杠归一化**：URL 被改写成 `/delay/3/`，
> 服务端 `rsplit("/", 1)[1]` 取到空串，延迟变成 0。
> 加 `?x=1`（带查询串时引擎不补尾斜杠）后探针才有效。
> **这是 A1 在真实场景里第一次咬到人，值得记一笔。**

### A9 ⭐⭐ `request.timeout` 与「连接失败」**同为退出码 1**

这是本轮最重要的单条发现。把 A8 与「连接被拒」的错误文本并排看：

| 场景 | 退出码 | 错误文本特征 |
|:---|:---:|:---|
| **请求超时** | **1** | `context deadline exceeded (Client.Timeout exceeded while awaiting headers)` |
| 连接被拒 | **1** | `dial tcp 127.0.0.1:9999: connectex: No connection could be made because the target machine actively refused it.` |

**两者退出码完全相同**，因为 `1 = GeneralFail` 是引擎的**兜底码** ——
凡是没有被 `errorsMap` 收录的错误，一律返回 1（见 A17 的源码）。

**对平台的影响**：归因判别器必须在 `exit=1` 内部做**二级分流**，
按错误文本特征区分 `timeout` 与 `environment`，否则「服务太慢」和「服务连不上」
会被报成同一类问题 —— 而这两件事的处置方式完全不同。

**辅助证据**：超时场景的 `elapsed(ms)` 精确等于 timeout 值 × 1000（实测 1008），
可作为交叉验证。

### A15 ⭐⭐ 官方退出码表（`hrp/internal/code/code.go`，v4.3.6 逐码抄录）

本轮从官方源码取得了**权威**的退出码定义，取代了此前的区间猜测：

```go
// general: [0, 2)
Success = 0; GeneralFail = 1

// environment: [2, 10)   ← ⚠️ 只定义了 9，2-8 是预留但未分配
InvalidPython3Venv = 9

// loader: [10, 20)
LoadFileError 10 / LoadJSONError 11 / LoadYAMLError 12 / LoadEnvError 13 /
LoadCSVError 14 / InvalidCaseFormat 15 / UnsupportedFileExtension 16 /
ReferencedFileNotFound 17 / InvalidPluginFile 18

// parser: [20, 30)
ParseError 20 / VariableNotFound 21 / ParseFunctionError 22 /
CallFunctionError 23 / ParseVariablesError 24

// runner: [30, 40)
InitPluginFailed 31 / BuildGoPluginFailed 32 / BuildPyPluginFailed 33 /
InterruptError 38 / TimeoutError 39

// summary: [40, 50)  ← 空

// 移动端 / CV：50-85（iOS 50-56、Android 60-66、UI 70-78、CV 80-85）
```

**三条必须记住的推论**：

1. **`2` 不是"环境错误码"。** 源码注释把 `[2,10)` 标为 environment，
   但实际只实现了 9。因此实测中出现的所有 `2` 都来自 **Go panic**（见 ③）。
   换言之，**`exit=2` 实质上是 panic 的签名**。
2. **`38` / `39` 住在 runner 区间，但语义是"中断"与"超时"。**
   按"runner 区间 = 执行机问题"一刀切，会把这两者误判成 ops —— 这是实质错误。
3. **`1 = GeneralFail` 是兜底码**，不携带任何分类信息（A9 已实证）。

**暴露的归因规则**（与 `internal/parser/attribution.go` 的实现一一对应）：

| 优先级 | 条件 | 归因 |
|:---:|:---|:---|
| 1 | 平台标记 Canceled | `canceled` |
| 2 | 平台标记 TimedOut | `timeout` |
| 3 | `exit == 0` | `pass` |
| 4 | **stderr 含 `panic:`** | `system_under_test` |
| 5 | `exit == 1` → 按错误文本分流 | `timeout` / `environment` |
| 6 | `exit == 9 / 31 / 32 / 33` | `ops` |
| 7 | `exit == 38` | `canceled` |
| 8 | `exit == 39` | `timeout` |
| 9 | `exit == 10–18` | `case_issue` |
| 10 | `exit == 20–24` | `case_issue` |
| 11 | `exit == 50–85` | `case_issue`（平台不支持移动端/CV） |
| 12 | 其他（含**无 panic 的 `exit=2`**） | `unknown` |

> **第 12 条是刻意的**：`exit=2 且无 panic` 无法解释，平台**选择不猜**，
> 归 `unknown` 并把原始日志交给用户。宁可不判，也不能把被测系统的问题
> 错判成执行机的问题 —— 那正是 F8 警告的失败模式。

### A16 ⭐ 步骤级状态的判据（F8 的一个推论）

断言失败会 panic（③），而 panic 时引擎停在 `run step start`、
**不会有配对的 `run step end`**。由此可导出：

> **一个带 `run step end` 且 `success=false` 的步骤，其失败原因一定不是断言不通过。**

因为它根本走不到 end。所以：

| 引擎轨迹 | 语义 | 步骤状态 |
|:---|:---|:---:|
| 有 `run step end`，`success=true` | 步骤跑完且断言全过 | `pass` |
| 有 `run step end`，`success=false` | 步骤**没跑完**（请求失败/变量未定义/hook 抛错） | `error` |
| **没有** `run step end` | 走到了断言阶段才 panic → 被测行为不符预期 | `fail` |

这把「步骤级 pass/fail/error」从主观判断变成了一条可复现的规则，
也让步骤级状态与整例归因保持一致（"失败"=被测系统的锅，"错误"=平台侧的锅）。

**两个值得单独记下的观察**：

1. **断言失败时 `summary.json` 确实完全不产出** —— 两种变体（首步失败、第二步失败）
   都验证了这一点，③ 的结论得到加固。
2. **失败步骤在 summary.json 里的形状与成功步骤完全不同**：
   成功步骤有 `data.req_resps` + `data.validators`；失败步骤**没有 `data` 段**，
   错误文本放在顶层 `attachments` 字段里。解析器必须同时处理这两种形状，
   否则"连接被拒"这类失败会只剩一个 `success=false` 而没有任何原因。

### A18 stdout 里 `hrp exit N` 会污染报文块

采集夹具时发现的一个解析陷阱：

请求失败时 stdout 是「只有 request 块 + `hrp exit 1`」，**没有 response 块、
也没有块尾分隔线**。若解析器按"分隔线切块"，`hrp exit 1` 会被并进请求体，
用户在页面上看到的「请求体」就变成了 `hrp exit 1`。

**修法**：把 `^hrp exit \d+$` 当作**块终止符**处理
（见 `internal/parser/stream.go` 的 `reExitLine`）。

### A20 ⭐⭐⭐ 遥测（GA4 + Sentry）默认开启，代价是每次执行 0.3–3.5 秒，还会污染错误摘要

*（第三轮补测。发现的契机：M1 端到端冒烟里，一条 `status=success` 的执行耗时突然
从 1.4s 变成 6.9s，且 `error_msg` 里赫然写着遥测上报失败。）*

#### 开关长什么样（v4.3.6 源码）

```go
// hrp/internal/env/env.go —— 包级 var，在 init 阶段就读掉了
DISABLE_GA     = os.Getenv("DISABLE_GA")
DISABLE_SENTRY = os.Getenv("DISABLE_SENTRY")

// hrp/internal/sdk/ga4.go
func SendGA4Event(name string, params map[string]interface{}) {
	if env.DISABLE_GA == "true" { return }     // ← 字符串相等比较，不是布尔解析
	...
	err := ga4Client.SendEvent(event)
	if err != nil {
		log.Error().Err(err).Msg("send GA4 event failed")   // ← 用 error 级打日志
	}
}

// hrp/internal/sdk/sentry.go
func init() {
	if env.DISABLE_SENTRY == "true" { return }
	...
}
```

三个必须记住的细节：

1. **只能用环境变量关，没有 CLI 参数**（`hrp run --help` 里没有任何 telemetry 相关 flag）。
2. **值必须是字面量 `"true"`**：代码是 `== "true"`，写成 `1` / `TRUE` / `yes` 一律无效。
3. **必须在子进程启动前设好**：`env.DISABLE_GA` 是包级变量，在 Go 的包初始化阶段
   就完成赋值，进程起来之后再 `os.Setenv` 没有任何作用。

#### 代价实测（`testdata/telemetry-probe/cases/`，各跑 3 次取最快）

| 夹具（退出码） | 引擎默认 | 两个都关 | 节省 |
|:---|---:|---:|---:|
| `pass.yml`（0，用例通过） | 1958 ms | 1490 ms | 23% |
| `dead.yml`（1，请求失败） | 1741 ms | 1487 ms | 14% |
| `fail_assert.yml`（2，断言失败 panic） | 2200 ms | 1482 ms | **32%** |

**关键不在百分比，而在"不稳定"**：关掉之后三条路径都稳定在约 1.48 秒；
不关的时候同一夹具在不同轮次能跑到 1.3s ~ 5.1s。原因是遥测上报是外网调用
（GA4 用的是页面上同一个 `api_secret`，HTTP client 超时 **5 秒**），
耗时完全取决于当时 DNS 与外网可达性 —— 内网环境直接跑满 5 秒。平台侧表现为：

- 同一份用例的「执行耗时」毫秒级跳动好几秒，看起来像是被测服务不稳定；
- 10 人团队并发执行时，每个执行都白占一个并发槽几秒钟。

最初那次 6.9s 就是极端情况：GA4 与 Sentry 各等满一次超时。

#### 二次伤害（比慢更糟）：上报失败会被当成用例错误

`log.Error()` 打出来的那条：

```json
{"level":"error","error":"request GA4 failed: Post \"https://www.google-analytics.com/mp/collect?api_secret=...\": context deadline exceeded","message":"send GA4 event failed"}
```

在 stderr 里与「用例失败」**完全同形**。平台的错误提取是按"最后一条 error 级日志"取的，
于是实测出现过一条 **`status=pass`、`panic=false` 的成功执行，`error_msg` 却是
`request GA4 failed: ... context deadline exceeded`**。

对用户的观感是：绿色通过的执行挂着一条看不懂的红色错误；更坏的情况是真的有失败时，
遥测噪音可能把真正的错误挤掉（遥测通常在进程退出前最后打）。

#### 平台落地（两层）

| 层 | 位置 | 做法 |
|:---|:---|:---|
| **第一层（治本）** | `internal/executor` 的 `caseEnv` | 按 `engine.disable_telemetry`（默认 true）注入 `DISABLE_GA=true` / `DISABLE_SENTRY=true`。用**覆盖式**写入而不是 append —— 父进程已有同名键时，Windows 的 `GetEnvironmentVariable` 取第一个匹配项，会被旧值顶掉 |
| **第二层（兜底）** | `internal/parser` 的 `lastErrorText` | 按**前缀**过滤 `request GA4 failed` / `send GA4 event failed` / `init sentry sdk failed`。只匹配前缀而不搜关键词：用户用例自己去请求 `google-analytics.com` 时报错文本是 `do request failed: Get "https://..."`，前缀不同，不会误伤 |

⚠️ 教训：`configs/config.example.yaml` 里**早就写了**"引擎会读取 DISABLE_GA / DISABLE_SENTRY
环境变量"，但代码里从未接线（`Engine.DisableTelemetry` 是个只有声明没有使用的字段）。
**配置项只要没有测试断言它真的生效，就等于没有实现。**

## 10. 复现方式（第三轮：A1 补充）

A1 的表格在后两行（`params: {}` / `params: null`）是补测的，目的是确认
「能不能用空 `params` 块规避补斜杠」。夹具已入库：`testdata/slash-probe/cases/s3_params_empty.yml`。

```bash
export HRP_PLATFORM_TOOLS=F:/httprunnerplatform-tools
HRP="$HRP_PLATFORM_TOOLS/bin/hrp.exe"
python testdata/local-echo/echo_server.py &      # 监听 127.0.0.1:8899

cd testdata/slash-probe
"$HRP" run cases/s3_params_empty.yml 2>/dev/null | grep -E '^(GET|POST) /'
# 实测输出（v4.3.6）：
#   GET /anything/abc/ HTTP/1.1        ← step1 params: {}    被补
#   GET /anything/abc/ HTTP/1.1        ← step2 params: null  被补
#   GET /anything/abc?k=v HTTP/1.1     ← step3 有真实 params 不补
#   GET /anything/abc?inline=1 HTTP/1.1 ← step4 URL 自带 ?     不补
```

⚠️ 这条复现**必须用 local-echo 服务**（它对任意路径都回 200）：
若换成一个对 `/anything/abc/` 返回 404 的服务，第一步就会因断言失败触发
failfast，后面三步根本不会执行，会误以为"只补了一次"。

## 11. 复现方式（第四轮：A20 遥测开销）

夹具已入库：`testdata/telemetry-probe/cases/{pass,dead,fail_assert}.yml`
（分别覆盖退出码 0 / 1 / 2 三条路径）。

```bash
export HRP_PLATFORM_TOOLS=F:/httprunnerplatform-tools
HRP="$HRP_PLATFORM_TOOLS/bin/hrp.exe"
python testdata/local-echo/echo_server.py &      # 监听 127.0.0.1:8899

cd testdata/telemetry-probe

# 各跑 3 次取最快，对比"引擎默认"与"关掉遥测"
t() { f="$1"; shift; best=999999
      for i in 1 2 3; do S=$(date +%s%N); env "$@" "$HRP" run "cases/$f" >/dev/null 2>&1
        E=$(date +%s%N); M=$(( (E-S)/1000000 )); [ $M -lt $best ] && best=$M; done
      echo "$best"; }
for f in pass.yml dead.yml fail_assert.yml; do
  printf "%-18s 默认 %5s ms   全关 %5s ms\n" "$f" "$(t $f)" "$(t $f DISABLE_GA=true DISABLE_SENTRY=true)"
done
```

实测输出（本机，v4.3.6）：

```
pass.yml             默认  1958 ms   全关  1490 ms
dead.yml             默认  1741 ms   全关  1487 ms
fail_assert.yml      默认  2200 ms   全关  1482 ms
```

**注意**：默认那列在不同轮次会大幅波动（本机实测区间 1.3s – 5.1s），
关掉之后才稳定。判据要看"是否稳定"而不是只看一次的数字。

验证"第二层防线"（错误摘要不会被遥测污染）可以在关掉遥测的前提下人为复现：
把上表的默认列跑一遍，观察 stderr 里是否出现
`{"level":"error","error":"request GA4 failed: ..."}` —— 出现即说明遥测已开。
