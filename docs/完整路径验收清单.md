## 一、起服务（三条命令）

```bash
# 1) 载入环境（每次新开终端都要做）
cd /f/httprunnerplatform && source scripts/dev-env.sh

# 2) 后端（用 Bash 起）
cd /f/httprunnerplatform && ./.smoke/hrpp.exe server -c .smoke/config.yaml

# 3) 前端（另开一个终端）
cd /f/httprunnerplatform/web && HRP_API_TARGET=http://127.0.0.1:8127 npm run dev
```

就绪确认：`curl -s --noproxy '*' -o /dev/null -w "%{http_code}" http://127.0.0.1:8127/healthz` → `200`。
登录：`http://127.0.0.1:5173`，`admin` / `admin123`。

> **三个高频坑**（详见验收指南 3.4）：① `curl` 访问本地服务不加 `--noproxy '*'` 会返回 502；
> ② 起前端忘了 `HRP_API_TARGET` 会连到 8080 上；③ 后端要重新编译前必须先 `source scripts/dev-env.sh`。
> 杀进程用 PowerShell（`Get-Process hrpp | Stop-Process -Force`），起服务用 Bash。

## 六、明确边界：这些不是 bug

验收时看到下面这些，请记为**预期行为**，不要当缺陷报：

| 现象 | 为什么是这样 |
|:---|:---|
| 断言失败时没有 HTML 报告 / summary | HttpRunner v4.3.6 的已知缺陷：断言失败会让引擎 panic，报告与 summary 都不产出。平台自己重建明细 |
| 执行进度是 1 秒轮询，不是实时推送 | WebSocket 进度推送是 M2 裁剪项，契约里保留定义以便后续接入 |
| 没有通知（企微/钉钉/Webhook/邮件） | M2 裁剪项：`notify_config` 表与字段都预留了，发送器未实现。当前靠 CI 令牌 + 流水线结果兜底 |
| 用例步骤里没有「接口定义库 / 引用其它用例」 | M2 裁剪项：`api_def` 表已建但无 CRUD；步骤类型 `api`/`testcase` 在编译器里明确报「尚未开放」 |
| 不能写 `debugtalk.py` | 实测需要全局 venv + PyPI 网络，且插件路径可能无限挂起（引擎无超时保护）；十人团队的接口用例基本用不上 |
| 没有 UI 自动化 / 性能测试 / OpenAPI 解析 | 明确不做（见项目方案 10.2） |
| 期望 `"185"` 但实际是 `185`，断言失败 | 类型严格比对是刻意行为，不是缺陷 |
| 跑一次计划却冒出多条执行记录 | 计划里挂 N 个用例集就产生 N 条（刻意的失败隔离设计），列表会折叠展示 |

## 七、高风险区（值得多试几次）

这几处是「设计上最容易出错、错了也不报错」的地方，建议每个都多试一轮：

1. **静默假绿**：畸形用例被引擎吞掉却退出码 0 —— 只有对账能抓出来（H10/F7）。
2. **cron 与时区**：错位不报错，只让计划在错误的时间跑，往往几周后才发现（G5）。
3. **`abort` 与取消**：预期用例数必须收缩，否则每次中止都刷一堆无意义的对账警告（F6/H2）。
4. **软删 / 禁用的成员**：既要「不静默跳过」，也要「不计入预期数」（F8/F9）。
5. **失败运行里的重建数据**：URL 和断言明细都是平台拼的，来源标注错了会让人误以为是引擎的结论（H5/BUG-003）。
6. **导出包能不能独立跑**：导出的东西如果只有平台自己能跑，"导出"就等于没做（L2）。
7. **重入保护**：跑得久的用例集 + 高频 cron，是唯一能把执行堆成山的组合（G7）。
