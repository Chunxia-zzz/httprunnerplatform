# httprunnerplatform · 项目方案

> 一个基于 HttpRunner 引擎的接口自动化测试平台
>
> 仓库：https://github.com/Chunxia-zzz/httprunnerplatform

| 项 | 内容 |
|:---|:---|
| 项目定位 | 面向小型测试团队的**接口自动化测试平台**（私有化部署） |
| 底层引擎 | **HttpRunner v4.3.6**（`hrp` 二进制），不改引擎、不 fork |
| 后端 | **Go**（Gin + GORM + MySQL 8） |
| 前端 | **Vue 3 + Vite + TypeScript + Element Plus** |
| 交付形态 | 单个可执行文件（内嵌前端）+ 一个数据库 |
| 产品形态 | **私有化部署**，非 SaaS |
| 目标规模 | ~10 人测试团队 |

---

## 一、项目目的

### 1.1 一句话定位

把 HttpRunner 从「**手写 YAML + 敲命令行 + 报告散落在磁盘上**」的工具，变成「**页面上写用例、点一下就调试、定时/流水线自动跑、失败能直接看出是谁的问题**」的团队级平台。

### 1.2 现状痛点（为什么需要这个平台）

使用 HttpRunner 的原生方式存在这些问题：

| 痛点 | 具体表现 |
|:---|:---|
| **门槛在 YAML 上** | 用例是 YAML 文件，缩进错一层就加载失败；团队成员必须手写 YAML，容易出错且不好 review |
| **命令行记忆负担** | 要记住 `hrp run xxx.yaml --gen-html-report --log-json ...` 一长串参数，没人记得全 |
| **没有用例资产概念** | 用例就是一堆文件，没有标签、模块、优先级、负责人、最近执行结果，找不到、不敢改 |
| **执行靠人** | 没有定时任务、没有批量执行；回归全靠人工逐个跑 |
| **流水线集成困难** | 引擎**没有任何官方执行 API**（这一点已核实，见 3.4-F2），CI 里只能自己拼命令行 |
| **失败信息不友好** | 只有一份 HTML 报告，说"失败了"，但**看不出是用例写错了还是被测系统有 bug**，也不知道失败发生在哪个步骤的哪个断言 |
| **报告散落** | 报告是磁盘上的 `report-<时间戳>.html` 文件，没有历史、没有趋势 |

### 1.3 目标用户与核心场景

**用户**：一个小型测试团队（约 10 人），其中有测试工程师和测试负责人；开发工程师与 CI 系统也需要接入。

| 角色 | 核心场景 |
|:---|:---|
| 测试工程师 | **在页面上写用例** → **单步骤调试** → 提交到用例集 → 看执行结果与失败明细 |
| 测试负责人 | 组织用例集 → 配置**测试计划**（定时/手动） → 看通过率与趋势 → 分派失败给对应负责人 |
| 开发工程师 | 通过 CI 触发计划，看到自己提交导致的失败 |
| CI 系统 | 用 Token 触发指定测试计划，**根据结果决定流水线成败** |

### 1.4 目标（可衡量的成功标准）

1. **写一条接口用例不需要打开编辑器、不需要写 YAML、不需要记命令行**——全程页面操作；
2. **调试单个步骤不超过 3 次点击**（不用跑完整条用例）；
3. **执行用例不需要人工触发**——测试计划支持定时，CI 可通过 API 触发；
4. **每条失败都能直接回答两个问题**：① 失败在哪个用例的哪个步骤的哪个断言？② **这是被测系统的问题，还是我们自己用例写错了？**（后者是本平台的核心差异化能力，见 6.3）
5. **不会出现"假绿"**——绝不会因为用例被静默跳过而显示全部通过（见 6.4）。

### 1.5 非目标（明确不做）

- ❌ **不做 SaaS / 多租户**。目标是自己人用的内网平台，SaaS 那一整套（租户隔离、配额计费、出网沙箱代理、排队公平性、控制面/数据面分离）对本项目是纯粹的负担。
- ❌ **不改造 HttpRunner 引擎**，不 fork 它的源码。
- ❌ **不做 UI 自动化**（Android/iOS/Browser）——那是 HttpRunner v5 的方向。
- ❌ **不做性能压测平台**（`hrp boom` 留作未来可选扩展）。
- ❌ 不做 Mock Server、测试数据工厂。

### 2.2 三个关键决策

#### 决策一：后端 Go，但**不引入 hrp 的 Go 库**

这是个反直觉的决定，值得说清楚。

**诱惑在哪**：hrp 本身就是 Go 写的，理论上可以直接 `import "github.com/httprunner/httprunner/v4/hrp"`，拿到官方类型定义和解析能力，省掉一堆事情。

**为什么放弃**——核实 `go.mod` 后的证据：

```
gocv.io/x/gocv v0.32.1            ← OpenCV 的 Go 绑定，需要 CGO + 构建机装 OpenCV
google.golang.org/grpc v1.57.0
github.com/prometheus/client_golang v1.13.0
github.com/shirou/gopsutil v3.21.11
github.com/getsentry/sentry-go v0.13.0
```

而 `hrp/config.go` 直接 `import "github.com/httprunner/httprunner/v4/hrp/pkg/uixt"`（UI 自动化 / CV 包）。**结论：主服务只要 import `hrp` 包，就会传递性拖入 OpenCV + CGO + gRPC + Prometheus 一整套重依赖。**

代价：编译必须开 `CGO_ENABLED=1`、**交叉编译基本失效**、二进制显著膨胀、依赖面变宽。

**次级证据**：进一步核对 `hrp/parser.go`，它**没有**任何「从 `[]byte` 或结构体解析出 TestCase」的公开入口；且 `extractVariables`、`findallVariables`、`mergeValidators` **全部是未导出的私有函数**。也就是说——**即使愿意付 CGO 的代价，能拿到的能力也非常有限**，变量依赖分析这类事情自己实现并不更困难。

**最终决策**：
1. 主服务保持轻量，**所有与引擎的交互走子进程**（`os/exec`）；
2. 静态校验**自研**（Go struct + 规则引擎），不依赖官方；
3. 若将来确实需要官方语义级校验，**写一个独立极小的工具**（`cmd/hrpctl`，单独 go module），让 OpenCV/CGO 的代价只落在它身上，主服务不受污染。

#### 决策二：前端 Vue 3 + Element Plus

- 与既有技术栈一致，无需重新学习；
- Element Plus 的 `Table` / `Form` / `Tree` / `Dialog` / `Steps` 组件最全，正好命中「重点是页面上操作」的需求；
- 中文文档最完善，团队其他人接手成本最低。

#### 决策三：私有化部署，非 SaaS

**SaaS 与私有化的本质差别不在功能清单，而在「你的用户是谁」**：私有化的用户是自己人（信任），SaaS 的用户是付费客户（必须假设有人恶意）。

由此派生的差异，以及本项目的结论：

| SaaS 必须做 | 本项目 | 理由 |
|:---|:---:|:---|
| 租户与数据隔离 | ❌ 不做 | 只有一群自己人，没有"别人的数据" |
| 配额 / 计量 / 计费 | ❌ 不做 | 内部平台不收钱 |
| 出网代理 + 域名白名单 | ❌ 不做 | **团队成员本来就有内网权限，用例直接连内网测试环境是正常需求，不该被限制** |
| 插件容器沙箱 | ❌ 不做 | RCE 对内网不构成威胁 |
| 排队公平性与防饿死 | ❌ 不做 | 峰值并发只有 2–4 个任务，FIFO 就够 |
| 控制面 / 数据面分离 | ❌ 不做 | 单机足够 |
| 数据合规自建 | ❌ 不做 | 走公司统一规范 |
| 多区域部署 | ❌ 不做 | — |
| **插件编辑权限收敛** | ✅ **做** | ⚠️ **但性质是「稳定性措施」而非「安全措施」**——防的是有人写死循环/误删文件拖垮执行机 |
| **执行超时限制** | ✅ **做** | 引擎默认 `case_timeout` 是 **3600 秒**，太长，一个卡死用例会占用执行槽一小时 |

**复杂度差距：SaaS 是私有化的 3–5 倍。本项目走 1× 的路。**

## 三、底层引擎事实基线

> 这一章是后续开发的**防踩坑清单**。其中标注 ⭐ 的都是读源码（而非读文档）才能发现的，官方文档里没有或写错了。

### 3.1 引擎概况与版本锁定

| 项 | 事实 |
|:---|:---|
| 项目 | HttpRunner（`hrp`），Apache-2.0，开源 |
| **锁定版本** | **v4.3.6（发布于 2023-09-19）** |
| 版本现状 | ⚠️ 该版本**之后三年没有新 release**；master 已转向 v5（纯 Go + LLM/UI 方向），**v5 无任何正式 tag**；Python 版拆到 `httprunner/httprunner.py`，该仓库也**零 release** |
| 分发方式 | 预编译二进制，覆盖 macOS(amd64/arm64) / Linux(amd64/arm64) / Windows(amd64)，**无运行时依赖** |
| 用到的子命令 | `run`（执行）、`convert`（导入转换）、`startproject`（脚手架）、`report`（补生成报告） |

**风险与应对**：引擎停更是事实，但**用例是纯文本 YAML，属性和平台解耦**。因此：
1. 锁定 v4.3.6 二进制并纳入版本管理；
2. **架构上把引擎当可替换组件**——执行器抽象成接口，未来可换 v5 或自研引擎；
3. 不 fork、不魔改源码。

### 3.2 核心概念 → 平台数据模型映射

| HttpRunner 概念 | 官方定义 | 平台映射 |
|:---|:---|:---|
| **TestCase** | 一个 YAML/JSON 文件 = 一条用例，结构**仅有** `config` + `teststeps` 两部分 | **用例** |
| **TestSuite** | 「一堆」用例；官方支持按多文件/文件夹运行 | **用例集**（见 5.3 的设计澄清） |
| **TestStep** | 最小执行单元，用例是有序步骤的集合 | **用例步骤** |
| **config** | 用例公共配置：name / variables / parameters / headers / verify / export / weight / think_time | **用例配置** |
| **api** | 可复用的单接口定义文件 | **接口定义库** |
| **项目根目录** | 相对路径的基准 | **执行工作区**（注意 F3：cwd 即根目录） |

**测试步骤类型（7 种）与增强能力：**

| 步骤类型 | 含义 | 增强能力 |
|:---|:---|:---|
| `request` | 直接发 HTTP 请求 | variables / setup_hooks / teardown_hooks / extract / validate |
| `api` | 引用 API 定义文件 | 同上 |
| `testcase` | 引用其他用例（**用例集就靠它**） | 同上 + export |
| `transaction` | 事务（性能测试用） | — |
| `rendezvous` | 集合点（性能测试用） | — |
| `think_time` | 思考时间 | — |
| `websocket` | WebSocket 请求 | 见 3.5 |

> ⚠️ **类型识别有优先级**：`api > testcase > think_time > request > transaction > rendezvous > websocket`。一个 step 里写了多个类型字段时按此顺序取一个。**平台表单要在 UI 层就避免这种歧义。**

### 3.3 平台必须支持的框架机制

| 机制 | 语法与说明 | 平台交互设计 |
|:---|:---|:---|
| **变量** | `$var` / `${var}` 两种引用；**四级优先级：`step variables` > `session variables`(extract 产生) > `parameter variables` > `config variables`**；`$$` 转义 `$`；**部分引用必须用 `${}`**（`abc${num}def` 对，`abc$numdef` 会把变量名识别成 `numdef`） | 变量面板 + 引用高亮 + 未定义校验 |
| **提取 extract** | jmespath 表达式或正则；提取对象**仅 5 类**：`status_code`/`proto`/`headers`/`cookies`/`body`；含 `-` 的字段名要加引号（`headers."Content-Type"`） | 提取配置器：选对象 → 填表达式 → 自动生成变量名 |
| **校验 validate** | 两种写法：简化 `- eq: ["status_code", 200]` 与对象 `check/assert/expect/msg`。**内置校验器**：`eq`/`equals`/`equal`、`lt`/`le`/`gt`/`ge`/`ne`、`str_eq`、`len_eq`/`len_gt`/`len_ge`/`len_lt`/`len_le`、`contains`、`contained_by`、`type_match`、`regex_match`、`startswith`、`endswith` | 断言可视化配置器（下拉 + 期望值） |
| **参数化 parameters** | 3 种来源：① 列表 ② CSV `${parameterize($file)}` ③ 自定义函数；策略 `sequential`/`random`/`unique`；`limit` 控制迭代次数；**短横线分组**（`username-password` 从 CSV 读 username/password 两列） | 参数集管理页 + CSV 上传 |
| **钩子 hooks** | `setup_hooks` / `teardown_hooks`；内置特殊变量 `$hrp_step_name` / `$hrp_step_request` / `$hrp_step_response` | 高级设置折叠区 |
| **环境变量** | ⚠️ **v4.1 起 `base_url` 已从 config 移到 `.env`**，用 `config.environs` 或 `.env` 文件导入 | **环境管理 = `.env` 文件管理** |
| **自定义函数** | `${func($a, $b)}`；插件文件 `debugtalk.py`（Python，免编译）或 `debugtalk.bin`（Go，需 `hrp build`）；**必须放项目根目录** | ⛔ **M1–M4 不支持**（见下方说明） |
| **转换导入** | `hrp convert` 支持 HAR / Postman / curl / pytest / gotest 自动识别 | 用例导入功能 |

### 3.4 ⭐ 源码级与实测级关键事实（官方文档没有或写错）

> 前 7 条来自源码阅读（含官方文档写错之处），**F8 起为 13.2 六项实测的产出**。全部实测证据见《引擎实测记录》。

| # | 事实 | 证据 | 对平台的硬性要求 |
|:--|:---|:---|:---|
| **F1** ⭐ | **日志与报文分走两条流**：引擎日志 → `stderr`（JSON Lines）；**请求/响应明细 → `stdout`（纯文本）** | `hrp/cmd/root.go` 的 `initLogger()`：JSON 模式 `writer = os.Stderr`。但实测发现 stdout 并非只有 `hrp exit N`——**每步还会打印约 15 行纯文本的请求响应快照**（受 `--log-requests-off` 控制）。且 `hrp exit N` **只在进程正常退出时出现，panic 退出（exit=2）时完全没有** | **执行器必须同时接两条管道、分别解析**：stderr 走 JSON Lines 状态机，stdout 按 `request`/`response`/分隔线分块。见《引擎实测记录》2.1 |
| **F2** ⭐ | **v4.3.6 没有 `server` 子命令** | v4.3.6 的 `hrp/cmd/` 只有：`root.go`/`run.go`/`boom.go`/`build.go`/`convert.go`/`pytest.go`/`scaffold.go`/`wiki.go`/`adb/`/`ios/`。`server`/`mcp-server`/`mcphost` 是 v5 才有的 | **引擎没有任何官方执行 API** → 调度层必须自建（这正是本平台存在的原因之一） |
| **F3** ⭐ | **cwd 就是项目根目录** | `hrp/internal/env/env.go`：`RootDir, err = os.Getwd()` | 子进程**必须显式设置 `cmd.Dir = 工作区路径`**，否则所有相对路径引用（`api/`、`data/*.csv`）全部失效 |
| **F4** ⭐ | **退出码是分区间设计的失败分类器（但断言失败例外，见下）** | `hrp/internal/code/code.go`：0/1 → `[2,10)` 环境 → `[10,20)` loader → `[20,30)` parser → `[30,40)` runner → `[40,50)` **为空** → `[50,90)` 设备/UI/CV | **可实现「失败归因自动二分」**（见 6.3）。⚠️ 但**断言失败不遵守这个设计**：它触发 Go panic，落到 `2`（环境区间）—— 归因必须以 `stderr 是否含 panic:` 为主判别器 |
| **F5** ⭐ | **loader 会静默吞掉格式错误的用例文件** —— ✅ **已实测坐实** | `hrp/loader.go`：`tc, err := testCasePath.ToTestCase(); if err != nil { return nil }`。实测：4 个可发现文件放入 1 个畸形 YAML，**该文件被静默丢弃，零 warn/零 error，退出码 0，summary 显示 3/3 全通过** | **最危险的「假绿」**：坏文件不执行、不报错、退出码仍是 0。→ 必须做执行前校验 + **执行后用例数对账**（见 6.4） |
| **F6** ⭐ | **`--case-timeout` 默认 3600 秒，且官方文档未记录此参数** | `hrp/cmd/run.go`：`runCmd.Flags().Float32Var(&caseTimeout, "case-timeout", 3600, ...)` | 平台默认值**下调到 300–600 秒**并可配 |
| **F7** | **hrp 会向 Google Analytics 4 与 Sentry 外发数据** | `hrp/internal/env/env.go` 暴露 `DISABLE_GA` / `DISABLE_SENTRY`；源码有 `hrp/internal/sdk/ga4.go`、`sentry.go` | 内网环境建议设置 `DISABLE_GA=1` `DISABLE_SENTRY=1`——**主要目的是避免无谓的外网请求超时拖慢执行**（内网环境下性质是性能问题，不是合规问题） |
| **F8** ⭐⭐ | **断言失败会触发 Go panic**（不是干净退出） | 实测四种断言失败（status/body 路径/header/多步第二步）**全部** panic，退出码 **2**。根因 `hrp/internal/builtin/assertion.go:53` 把未初始化的 `*testing.common` 传给 `testify`：断言**通过**时不触发 `Fail()` 故无异常，断言**失败**时 `Fail()→Errorf()→common.decorate()` 空指针 | **引擎在能力上无法报告断言失败**。→ 归因不能只看退出码（6.3）；→ 断言失败时不会产出 summary.json / report.html，平台必须自行重建结果（6.6） |
| **F9** ⭐ | **URL 尾斜杠自动归一化**（官方文档未记录） | 实测：最终 URL **不带查询串**时 hrp 给路径补 `/`（`/anything/abc` → `/anything/abc/`，GET/POST 皆然）；**带查询串**（inline `?x=y` 或 `params:`）时不补，原路径保留 | 对 Spring Boot / Django 等严格路由会 404 或 301。→ **调试视图与报告必须展示「最终生效 URL」**（取自 stdout 快照或 summary.json），而非 YAML 原文；编辑器需给出提示 |
| **F10** ⭐⭐ | **`hrp run <目录>` 是「全有或全无」** | 实测三个用例（通过→失败→通过）：第 2 个 panic 后**第 3 个根本没执行**，且**该批全部结构化结果丢失**（含已通过的第 1 个）。`--continue-on-failure` 在 panic 前无效 | **必须一个用例一个子进程**（见 6.5）。这是执行器的基本架构约束 |
| **F11** | **summary.json 里没有任何源文件路径** | `details[].root_dir` 实测恒为 `""`；`details[]` / `records[]` 中无文件路径字段，唯一标识是 `config.name` | 多用例混跑时结果无法回填到用例 → 由 F10 的「一对一执行」解决；另需**编译期强制 `config.name` 唯一** |

**另外几条重要补充：**

- **官方对「平台化」零指导**：`docs/user-guide/integrate/extend`（框架能力扩展）与 `docs/user-guide/integrate/integrate`（测试平台集成）**两个文档页都是空壳**，只有标题。`--log-json` 是官方唯一的集成手段，且其输出格式**无 schema、无版本化承诺**。
- **官方 v4 尚未实现的两件事**（版本对比表标注为 TODO）：
  - **`jsonschema` 脚本格式校验** → 官方**没有** schema 校验，平台必须自建；
  - **`skip` 机制** → 用例/步骤**没有原生跳过能力**，平台的「临时禁用某步骤」只能在**编译期从 YAML 里剔除该步骤**。
- **官方文档自相矛盾之处**（按保守理解设计）：
  - `validate` 正文说断言「不支持自定义拓展」，但同页示例注释说「可以自定义」→ **平台按"不支持"设计，断言配置器硬绑内置校验器清单**；
  - 版本对比表（2022-05）把 Postman/Swagger/Curl 标注为"计划支持"，但 `convert` 文档（2022-06）已说明支持 HAR/Postman/curl 自动识别 → **Swagger/OpenAPI 至今未见落地**，若要做需自建解析器。
- **`go.mod` 里有 `github.com/go-openapi/spec v0.20.7`（直接依赖）** → 内部可能已有 OpenAPI 解析能力但未在命令与文档中暴露，值得后续单独确认。
- **⛔ 关于 `debugtalk.py`：M1–M4 明确不支持。** 实测（《引擎实测记录》2.6）：
  - **项目中不放 `debugtalk.py` 时，Python 依赖链可被完全绕开** —— 六个探针工程均无插件文件，全部正常运行，stderr 中没有任何 venv 准备步骤，**零开销**；
  - **一旦放入 `debugtalk.py`**：hrp 会 fork python 做 AST 扫描（~800 ms）→ 生成 `.debugtalk_gen.py` 写进**项目根** → 要求一个**全局共享 venv**（`~/.hrp/venv`，不是项目级）里装有 `funppy`；
  - `funppy` 是**重依赖**（`grpcio` + `grpcio-tools` + `protobuf` + `setuptools`，数十 MB 级 wheel）；本机 `pip install funppy` 实测**失败**（5.4 s）→ 退出码 9；即便 `funppy` 已就绪，插件路径**无限挂起**（>2 分钟无输出无退出，hrp 自身无超时保护）；
  - hrp 还会通过 `cmd.exe` 派生 `python.exe` 子进程 → 取消执行时必须按**进程树**杀。
  → **结论**：引入 `debugtalk.py` 会把「全局 venv 运维 + PyPI 网络可达 + 无限挂起防护」三件事一起拖进平台。十人团队的接口用例绝大多数不需要 Python 自定义函数；若确有需要（如签名计算），用平台内置的 Go 侧变量函数替代，或放到后续独立里程碑（强制预置 venv + 强制超时）。
- **hrp 会往项目根写产物**：`results/`、`.debugtalk_gen.py`、`__pycache__/` → 绝不能直接对用户受版本管理的用例目录执行；平台脚手架工作区的 `.gitignore` 需排除 `results/`、`__pycache__/`、`.debugtalk_gen.py`。
- **`level=warn` 不等于异常**：`locate plugin failed` 是**每个用例每次执行都产生**的常驻噪音（即使项目里没有任何 `debugtalk.py`）→ 日志视图必须白名单过滤，否则用户天天看到假告警。

### 3.5 WebSocket 步骤的能力矩阵（表单需按 `type` 条件渲染）

WebSocket 有 6 种操作类型，**每个类型支持的字段完全不同**：

| 操作 | 超时 | 请求头 | 阻塞 | 可发消息 | 状态码 | 提取/断言 |
|:---|:---:|:---:|:---:|:---:|:---:|:---|
| `open` | ✅ | ✅ | ✅ | ❌ | ❌ | ✅（同 HTTP：proto/status_code/headers/cookies/body） |
| `ping` | ✅ | ❌ | ❌ | ✅ | ❌ | ❌ |
| `w` | ❌ | ❌ | ✅ | ✅ | ❌ | ❌ |
| `r` | ✅ | ❌ | ✅ | ❌ | ❌ | ✅（**仅 body**） |
| `wr` | ✅ | ❌ | ✅ | ✅ | ❌ | ✅（**仅 body**） |
| `close` | ✅ | ❌ | ✅ | ✅ | ✅ | ✅（仅 `status_code` + `body`） |

**对数据模型的影响**：`teststep` 表不能用通用的 `request` JSON 字段兜住 WebSocket，需要独立的 `ws_op_type` + `ws_payload` 字段，且表单字段可用性由 `type` 驱动。

**已知限制**：har2case **不支持** WebSocket 包转换；**无自动重连**；二进制消息的提取/断言目前转字符串处理；ping 的 pong 接收是异步的，**不支持对 pong 断言**。

> **本期建议**：WebSocket 属于 M4 之后的扩展能力，M1–M3 先专注 HTTP(S)（即团队 95% 的需求）。但**数据模型现在就要留好字段**，避免后期改表。

**交付体验**：前端产物用 `go:embed` 嵌进二进制 → **最终交付是一个可执行文件 + 一个数据库**，内网部署与升级都极其简单。

> ✅ **已实现**（`internal/webui/`）。要点：
>
> - 构建入口是 `bash scripts/build.sh`：构建前端 → 同步到内嵌目录 → 编译后端，
>   之所以固化成脚本，是因为 `vite` 产出在 `web/dist`、而 `go:embed` 读的是
>   `internal/webui/dist`，中间那步"同步"靠人记得手动做，早晚会出现
>   「代码改了、界面没变」的幽灵问题。
> - **`NoRoute` 的分流顺序是这套机制里最容易坏的一处**：`/api/...` 必须永远
>   返回 JSON。若接口路径打错时落进 SPA fallback，前端拿到的是 200 + HTML，
>   axios 抛「Unexpected token '<'」，与真实原因（路径拼错）完全对不上。
>   这条约束由 `internal/api/router_test.go` 锁住。
> - 带扩展名却找不到的资源必须真 404，**不能**回 index.html —— 否则
>   `/assets/index-旧哈希.js` 会得到一份 HTML，浏览器同样报
>   「Unexpected token '<'」，把"前端换了版本 / 浏览器缓存了旧 HTML"
>   这个真实原因彻底掩盖掉。
> - 内嵌目录只提交一个 `.gitkeep`：全新克隆不装 Node 也能 `go build` /
>   `go test`，启动后访问 `/` 会看到一个明确的"前端未构建"提示页
>   （而不是白屏 —— 白屏会被当成 bug 去查）。
> - 启动日志打印内嵌文件数与构建时间（`scripts/build.sh` 写入 `build-id`），
>   用于判断"手里这个 exe 到底带的是哪一版前端"。

### 4.2 核心设计原则：**数据库是唯一真源，YAML 是可再生的编译产物**

这是整个系统最重要的一条设计决策。

```
用户在页面编辑  →  写 DB（结构化元数据）
                        │
                        │  执行时按需编译（单向、幂等）
                        ▼
              runtime/runs/{run_id}/  (一次性工作区)
                        │
                    hrp run
                        │
                  结果回写 DB
```

**推论：**

1. **不做双向同步**。「用户在服务器上手改 YAML 再反向同步回 DB」这条路**彻底封死**——它会带来无穷无尽的冲突合并问题；
2. YAML 只是「编译产物」，可随时全量重新生成，允许丢弃；
3. 前端提供**表单编辑**（主）+ **YAML/JSON 源码视图**（辅）；
4. 支持一键**导出整个项目为 hrp 标准目录**（单向、只读），便于归档与 code review。

**⭐ 这条原则带来的意外红利：**

> 官方 v4 恰好**没有 jsonschema 校验**（官方 TODO），而平台生成的 YAML 是**我们自己程序写出来的**——两个事实相遇的结果是：**「用例格式错」这一类问题被架构性消除了**。我们只需校验「业务规则」：引用是否存在、变量是否定义过。而这两类恰好对应引擎退出码 `17` 和 `21`，都是编译期能抓到的。

**唯一的风险入口是「源码视图」**：如果允许用户直接在 Monaco 里改 YAML，就把格式错的风险引回来了。
**对策**：源码视图保存时**必须严格反解析回结构化数据**，解析失败就拒绝保存并高亮报错——风险闭环。

### 4.3 工作区目录规范

每个项目对应一个 hrp 标准项目根目录：

```
{F:\httprunnerplatform 的部署目录}/data/
├── workspaces/{project_code}/        # 持久层：只有"源代码"
│   ├── .env                          # 环境变量（由环境模块渲染）
│   ├── debugtalk.py                   # 自定义函数（管理员维护）

│   ├── testcases/{case_code}.yaml     # 用例
│   ├── suites/{suite_code}.yaml       # 用例集
│   └── data/{dataset_code}.csv        # 参数化 CSV
└── runtime/                           # 运行层：可随时清理
    ├── runs/{run_id}/                 # 每次执行的隔离工作区副本
    └── reports/                       # HTML 报告归档
```

**设计要点**：持久目录与运行期目录**物理分离**。持久目录只放"源代码"，运行期全部丢到 `runtime/`，便于清理与备份。

### 5.3 ⭐ 概念澄清：用例集 ≠ 测试计划

这两个概念在很多平台里被混淆，本项目明确区分：

| 概念 | 定义 | 特征 |
|:---|:---|:---|
| **用例集（TestSuite）** | **用例的逻辑分组** | 静态、可复用、有执行顺序、能传递变量（`export`） |
| **测试计划（TestPlan）** | **执行安排** | 引用一个或多个用例集 + 指定环境 + **触发方式（手动 / 定时 / CI）** + 通知规则 + 超时 |

**这个区分的直接收益**：**「定时任务」不再是独立概念，而是测试计划的一个属性**（`trigger_type='cron'` + `cron_expr`），模型显著更干净。

**实现方式**：用例集在编译后是一个 **`teststeps` 全部为 `testcase` 引用类型**的 YAML 文件（而不是"一个文件夹"）。这样才能保留执行顺序、变量 `export` 传递、失败继续策略——比文件夹模式强得多。

## 六、核心机制设计

### 6.1 执行链路

```
① 提交执行（页面手动 / cron 定时 / CI 调 API）
   └→ 创建 run_record(status=queued)，投递到内存任务队列

② Worker 取任务
   └→ 状态改 running；在 runtime/runs/{run_id}/ 建立【独立工作区】

③ YAML 编译器 + 静态校验（Go，纯内存，不调引擎）
   ├─ 拉取计划/用例集/用例的完整元数据
   ├─ 渲染 .env（按 environment 配置）
   ├─ 生成 debugtalk.py（内置区 + 管理员自定义区）
   ├─ 生成 api/*.yaml、testcases/*.yaml、suites/*.yaml、data/*.csv
   ├─ 【校验】引用是否存在、变量是否定义、步骤类型是否冲突
   └─ 校验不过 → 直接判 error，不进引擎（这是正确性保证，不是优化）

④ 执行（循环：每个用例一个独立子进程）
   └→ for each case:
        exec.CommandContext("hrp", "run", "<单个用例文件>.yml",
                            "--log-json", "--save-tests", "--gen-html-report",
                            "--case-timeout", N)
      ★ 必须设置 cmd.Dir = 工作区路径        （F3：cwd 即项目根）
      ★ 目标参数必须是【单个文件】，不是目录 （6.5：目录模式一个失败就摧毁整批）
      ★ 必须【分别】接 stdout 与 stderr       （F1：日志在 stderr、报文在 stdout）
      ★ 必须设置进程组/Job Object，取消时杀整棵树
                                            （hrp 会派生 cmd.exe / python.exe 子进程）
      ★ 必须自行实现超时强杀
                                            （--case-timeout 不覆盖插件准备阶段，实测可无限挂起）
      ✗ 不要传 --continue-on-failure         （panic 面前无效）

⑤ 实时回传
   └→ 逐行解析 stderr 的 JSON → WebSocket 推送到前端（步骤级实时进度）

⑥ 结果落库
   ├─ 进程退出码 + stderr 是否含 panic: → 失败归因（6.3 判别器表）
   ├─ stderr JSON → step_result / assertion_result
   ├─ stdout 报文快照 → 步骤的最终生效 URL 与请求/响应明细（断言失败时唯一的明细来源）
   ├─ summary.json（若产出）→ 精确断言结果
   ├─ 断言失败时：用「无配对 run step end 的步骤」定位 + 平台自行比对期望/实际（6.6）
   ├─ 【用例数对账】期望 vs 实际 → 不一致则标 error 并告警
   └─ HTML 报告路径归档

⑦ 后置动作
   └→ 触发通知；更新用例的 last_run_id / last_status
```

### 6.2 并发、隔离、超时、取消

- **隔离**：每次执行复制出**独立工作区**。三重理由，缺一不可——
  ① `hrp run` 没有并发参数；② 报告/日志固定写在项目根（`results/`、`.debugtalk_gen.py`、`__pycache__/`）；
  ③ **`results/` 的时间戳精度只到「秒」**（实测 `results/20260922173020/`），同秒内的两次运行会落到**同一个目录**互相覆盖。**不隔离必然串台**；
- **并发**：进程内 worker pool，**默认 2–3 个并发**（4C8G 机器足够撑 10 人团队）；
- **超时**：`context.WithTimeout` + 兜底；超时后杀**进程树**。
  ⚠️ **不要把 `--case-timeout` 当作超时机制**：它只管单个用例的执行时长，**不覆盖插件准备等前置阶段**，实测该阶段可无限挂起（>2 分钟无输出、无退出）；
- **取消**：记录 PID 与进程组 ID（Windows 用 **Job Object**），前端「终止执行」按钮复用同一套杀进程逻辑。
  ⚠️ **不要依赖 shell 的 `timeout` 命令**——在 Windows 上它杀不掉 hrp 派生出的 `cmd.exe` / `python.exe`，会留下孤儿进程；
- **⚠️ 不要做的事**：不要上 Redis / MQ / K8s。10 人团队峰值并发只有 2–4 个任务，进程内队列完全够用。**留好 `Executor` 接口**，将来真需要横向扩展再换实现。

### 6.3 ⭐ 失败归因自动二分（核心差异化能力）

引擎退出码是**分区间设计**的，可以直接映射成失败根因：

| 退出码 | 官方含义 | 平台归因 | 谁的锅 |
|:---:|:---|:---|:---|
| 0 | Success | ✅ 全部通过 | — |
| **1** | GeneralFail | 🔴 **请求未完成**（连接被拒 / DNS 失败 / 超时） | **环境或被测服务** |
| **2** ⚠️ | *(官方表中为环境区间起始)* | 🔴 **断言未通过** —— 实为 **Go panic 退出码** | **被测系统** |
| 9 | InvalidPython3Venv | ⚙️ 执行机 Python 环境异常 | 运维 |
| 10 | LoadFileError | 🟡 用例文件读取失败 | 工作区/权限 |
| 11 | LoadJSONError | 🟡 用例 JSON 语法错误 | 用例（编译器应拦截） |
| 12 | LoadYAMLError | 🟡 用例 YAML 语法错误 | 用例（编译器应拦截） |
| 13 | LoadEnvError | 🟡 `.env` 加载失败 | 环境配置 |
| 14 | LoadCSVError | 🟡 参数化 CSV 加载失败 | 参数集 |
| 15 | InvalidCaseFormat | 🟡 用例结构非法 | 用例 |
| 16 | UnsupportedFileExtension | 🟡 文件类型不支持 | — |
| **17** | **ReferencedFileNotFound** | 🟡 **引用的接口/用例/CSV 不存在** | **用例（校验器应提前拦截）** |
| 18 | InvalidPluginFile | ⚙️ 插件文件非法 | 管理员 |
| 20 | ParseError | 🟡 解析失败 | 用例 |
| **21** | **VariableNotFound** | 🟡 **变量未定义** | **用例（编辑器应提前拦截）** |
| 22 | ParseFunctionError | 🟡 函数解析失败 | 自定义函数 |
| 23 | CallFunctionError | 🟡 函数调用失败 | 自定义函数 |
| 24 | ParseVariablesError | 🟡 变量解析失败 | 用例 |
| 31 | InitPluginFailed | ⚙️ 插件初始化失败 | 管理员 |
| 32 | BuildGoPluginFailed | ⚙️ Go 插件编译失败 | 管理员 |
| 33 | BuildPyPluginFailed | ⚙️ Python 插件构建失败 | 管理员 |
| 38 | InterruptError | ⏹️ 被用户终止 | — |
| 39 | TimeoutError | ⏱️ 执行超时 | 用例（调超时或优化用例） |

**⚠️ 实测修正（详见《引擎实测记录》2.3）：上表第 2 行必须改。**

`code.go` 的区间设计让「`1 = GeneralFail`」很容易被读成「断言失败」。**实测完全相反：**

| 场景 | 退出码 | 有 panic | summary.json | 真实语义 |
|:---|:---:|:---:|:---:|:---|
| 连接被拒（`127.0.0.1:9999`） | **1** | ❌ | ✅ **正常产出** | **用例没跑完** —— 请求/环境失败，`error: do request failed: Get "..."` |
| 断言不通过（期望 201 实际 200） | **2** | ✅ | ❌ **完全不产出** | **用例跑完了但断言不过** |

**根因（栈回溯，精确到源码行）**：`hrp/internal/builtin/assertion.go:53` 把**未初始化的 `*testing.common`** 传给 `testify`。
断言**通过**时不触发 `Fail()`，相安无事；断言**失败**时 → `Fail()` → `Errorf()` → `common.logDepth()` → `common.decorate()` → **空指针 panic**。

```
hrp/internal/builtin/assertion.go:53   → testify/assert.EqualValues → assert.Fail
  → testing.(*common).decorate → panic: invalid memory address or nil pointer dereference
  → hrp/response.go:198 → hrp/step_request.go:431
```

> **所以 `2` 落在「环境」区间纯属巧合 —— 它就是 Go runtime 未捕获 panic 的固定退出码，不是引擎的设计契约。**
> **结论：`hrp v4.3.6` 在能力上无法报告任何断言失败，它只会崩溃。** 平台的「失败归因」不能建立在「退出码区间」这个假设上。

**核心洞察（修正版）：**

> **退出码 `1` = 用例根本没跑完（请求/网络/服务不可用，环境侧）；退出码 `2` + `stderr` 含 `panic:` = 用例跑完了但断言不通过（被测系统侧）。**
> 两者**不能靠退出码单独区分**，因为 panic 也占用了 `2`。

**归因判别器（按优先级，可实现为纯函数）**：

| 优先级 | 判据 | 归因 |
|:---:|:---|:---|
| 1 | `exit_code == 0` | ✅ 通过 |
| 2 | `stderr` 含 `panic:` | 🔴 **断言失败 → 被测系统** |
| 3 | `exit_code == 1` | 🔴 **请求未完成 → 环境/服务** |
| 4 | `exit_code` ∈ {9,18,31,32,33} | ⚙️ 执行机/插件环境 → 运维 |
| 5 | `exit_code` ∈ {10..17, 20..24} | 🟡 用例或环境配置问题 → 用例维护 |
| 6 | 其他 | ⚠️ 未知，保留原始日志人工判定 |

**附带判别器**：`stdout` 是否含 `hrp exit N`。**含 → 进程正常退出；不含且退出码非 0 → 一定是 panic。**（panic 会跳过 `code.GetErrorCode()` 的打印）

**产品价值**：把「今天 12 条失败」自动拆成「**3 条是被测系统 bug、9 条是用例/环境问题**」，直接回答"该由谁处理"。**这是竞品普遍缺失的能力**，也是本平台最值得做的差异化功能。

**实现要点**：`code.GetErrorCode()` 会把退出码 `fmt.Printf` 到 **stdout**（`hrp exit N`），同时 `os.Exit(N)` 返回给父进程。
**以进程退出码为准，`stdout` 的 `hrp exit N` 作为「是否正常退出」的旁证**（而非取值来源 —— panic 时它不会出现）。

### 6.4 ⭐ 用例数对账（防「假绿」）

**✅ 已实测坐实**（详见《引擎实测记录》2.4）：往目录放 4 个可发现文件（1 个畸形 YAML + 3 个正常），实跑结果——

```
exit=0 ｜ 实际执行 3 条 ｜ summary.json 显示 3/3 全通过 ｜ 无任何 error ｜ 与畸形文件相关的日志只有一行 "load file"
```

`hrp/loader.go` 对出错的文件执行 `if err != nil { return nil }`——**格式错误的用例被完全静默地跳过，不执行、不报错、不告警、退出码依然是 0**。

**后果**：一个用例集本该跑 20 条，实际跑了 18 条，页面显示**全绿**。这是最危险的一类误报。

**两道对策：**
1. **执行前**：编译器产出后做静态校验，把退出码 17/21 这类问题挡在门外；
2. **执行后**：**强制对账** —— `expected_case_count` vs `actual_case_count`，不一致就把本次运行标为 `error` 并告警。**绝不因为「退出码 0」就断定全绿。**

**另两条实测副产品，同样要落进实现：**
- **扩展名白名单**：只有 `.yml` / `.yaml` / `.json` 会被发现（`.txt` **连 `load file` 日志都不产生**，在遍历阶段就被过滤）；
- **用例发现顺序 = 字节序（ASCII）字典序**，递归子目录，**不是自然排序**（实测 `Z_upper` 排在 `a_alpha` 之前）。
  → 编译器生成用例文件时应统一加**零填充序号前缀**，把执行顺序显式化、可控化。

### 6.5 ⭐⭐ 一对一执行：一个用例 = 一个独立子进程

**这是实测挖掘出的最关键架构约束**（详见《引擎实测记录》A2）。

`hrp run <目录>` 是**「全有或全无」**的。实测三个用例（通过 → 失败 → 通过）：

```
exit=2
实际执行:  BATCH-1-pass ✅ → BATCH-2-fail 💥 panic → BATCH-3-pass ❌ 从未执行
results/ :  (空) —— 连第 1 条通过的用例的结果也一起丢了
```

**原因链条**：任一用例断言失败 → **panic** → 进程死亡 → **后续用例根本不执行**（`--continue-on-failure` 在 panic 面前无效）→ **该批次全部结构化结果丢失**。

**因此执行器的基本单位必须是一个用例文件，而非目录：**

```
for each case in plan.cases:
    workspace = 独立工作区
    exec.CommandContext("hrp", "run", "<单个用例文件>", ...)   // 绝不用目录
    → 进程边界即结果归属边界
```

**额外收益**：正好补掉 6.6 里 summary.json 的致命缺陷 —— `details[].root_dir` 恒为空、结构里**没有任何源文件路径**，多进程混跑根本无法把结果回填到具体用例。**一对一执行让归属问题直接消失。**

**代价**：每用例一次进程启动（实测冷启动约 0.9 s）。对十人团队规模完全可接受，换来的是**故障隔离 + 结果确定性**。

**顺带移除**：命令行里的 `--continue-on-failure` 建议去掉（panic 面前无效，徒增理解成本）。

### 6.6 结果解析：多源互补策略

**⚠️ 关键前提：`--save-tests` 的 summary.json 在断言失败时完全不产出**（因为进程 panic 了，来不及落盘）。
也就是说，**最常见的失败类型恰恰没有结构化结果**。所以解析策略必须多源互补，而不是「主备降级」。

| 数据源 | 参数 | 拿到什么 | 全部通过 | 请求失败(exit 1) | **断言失败(exit 2)** |
|:---|:---|:---|:---:|:---:|:---:|
| **① stderr JSON Lines** | `--log-json` | 步骤起止、已通过的断言明细、extract、耗时、`error` | ✅ | ✅ | 🟡 **停在 `run step start`** |
| **② stdout 报文快照** | 默认开启（`--log-requests-off` 可关） | 每步**最终生效 URL**、请求头/体、响应状态/头/体 | ✅ | 🟡 只有请求段 | ✅ **唯一完整可用** |
| **③ summary.json** | `-s` / `--save-tests` | 结构化统计 + 步骤级断言结果 + `in_out` 变量 | ✅ | ✅ | ❌ **不产出** |
| **④ report.html** | `-g` / `--gen-html-report` | 人看的报告（**自包含单文件**，零静态资源） | ✅ | ✅ | ❌ **不产出** |

**三处必须落地的实现细节：**

1. **双流分离采集**：stdout 与 stderr **分别接管道、分别解析**，绝不能合并（F1 修正版）。
2. **断言失败时的结果重建**（平台必须自己算）：hrp 不会告诉你哪条断言错了，所以——
   - 用「**最后一条有 `run step start` 但没有配对 `run step end` 的步骤**」定位失败步骤；
   - 取该步的 stdout 报文快照作为**实际值**；
   - 从数据库取该步声明的断言作为**期望值**；
   - **平台自行比对，生成「期望 vs 实际」的展示**。这是「步骤级失败原因」在断言失败场景下**唯一**的可行来源。
3. **归因规则前置**：`stderr` 中 `panic:` 的出现与否直接影响归因结果 → **解析必须在归因之前完成**（见 6.3 判别器表）。

**解析器实现要求：**
1. 逐行 **try-parse**：能解析成 JSON 的按日志事件处理，解析不了的**直接丢弃**——
   ⚠️ **stderr 尾部可能是数百行 Go 栈回溯**，任何「先按行数取尾部」的做法都会拿到垃圾；
2. 字段缺失一律降级为 `null` 而**不抛异常**；
3. **`level=warn` 不等于异常**：`locate plugin failed` 是**每个用例每次执行都产生**的常驻噪音（即使项目里没有任何 `debugtalk.py`），必须白名单过滤，否则用户天天看到假告警；
4. **永久保留原始日志原文**——格式变化时可离线重放修复历史数据；
5. 给解析器写单测，锁死当前 v4.3.6 的格式。

### 6.7 YAML 编译器

**输入**：DB 中的结构化元数据（用例 + 步骤 + 环境 + 参数集）
**输出**：一个完整的 hrp 工作区

| 产物 | 来源 |
|:---|:---|
| `.env` | environment 表 |
| `debugtalk.py` | 平台内置函数区 + 管理员自定义区（**分区，用户不可直接改**） |
| `api/{code}.yaml` | api_def 表 |
| `testcases/{code}.yaml` | testcase + teststep 表 |
| `suites/{code}.yaml` | testsuite（`teststeps` 全为 `testcase` 引用） |
| `data/{code}.csv` | param_dataset 表 |

**示例对照**——DB 里的一条用例：

```json
{
  "code": "login_then_query_order",
  "name": "登录后查询订单详情",
  "config": { "variables": { "device_sn": "AAA001" } },
  "steps": [
    { "seq": 1, "step_type": "request", "name": "用户登录",
      "request": { "method": "POST", "url": "$base_url/api/login",
                   "body": { "username": "tester", "password": "123456" } },
      "extract": { "token": "body.data.token" },
      "validate": [ { "validator": "eq", "check": "status_code", "expect": 200 } ] },
    { "seq": 2, "step_type": "api", "name": "查询订单", "ref_api_code": "get_order",
      "variables": { "order_id": "10086" },
      "validate": [ { "validator": "eq", "check": "status_code", "expect": 200 } ] }
  ]
}
```

编译产出的 `testcases/login_then_query_order.yaml`：

```yaml
config:
  name: "登录后查询订单详情"
  variables:
    device_sn: AAA001
  export: ["token"]

teststeps:
  - name: "用户登录"
    request:
      method: POST
      url: $base_url/api/login
      headers:
        Content-Type: "application/json"
      body:
        username: tester
        password: "123456"
    extract:
      token: "body.data.token"
    validate:
      - eq: ["status_code", 200]
  - name: "查询订单"
    api: api/get_order.yaml
    variables:
      order_id: "10086"
    validate:
      - eq: ["status_code", 200]
```

用例集编译产出的 `suites/smoke_suite.yaml`：

```yaml
config:
  name: "冒烟用例集"

teststeps:
  - name: "登录后查询订单详情"
    testcase: testcases/login_then_query_order.yaml
  - name: "用户信息校验"
    testcase: testcases/check_user_profile.yaml
```

> **评审重点**：平台所有的"编辑"最终都要能**无损编译**成上面这种标准 hrp 用例。这是本方案的技术核心。

### 6.8 静态校验器（不是优化项，是正确性保证）

因为存在「假绿」风险（F5），执行前的校验是**必需**的。校验项：

| 校验项 | 对应退出码 | 何时拦截 |
|:---|:---:|:---|
| 引用的 `api` / `testcase` 是否存在 | 17 | 保存时 + 执行前 |
| 引用的 CSV 文件是否存在 | 14 | 保存时 + 执行前 |
| 变量是否定义过（含四级优先级解析） | 21 | 保存时（编辑器实时提示） |
| 步骤类型是否冲突（一个 step 多个类型字段） | 15 | 保存时 |
| 断言校验器是否在内置清单内 | — | 保存时 |
| 计划引用的用例集/环境是否有效 | — | 保存时 + 执行前 |
| 步骤的 `findallVariables` 依赖顺序（变量引用变量） | 24 | 执行前 |

**编辑器里的变量校验器必须实现三件套**（见 3.3）：**优先级解析 + `${}` 边界识别 + `$$` 转义**。否则会误报/漏报。**这是用例编辑器里工作量最大的单一模块。**

```json
POST /api/v1/runs

  "target_type": "plan",

  "trigger_type": "manual",
  "options": { "gen_html_report": true, "case_timeout": 300, "concurrency": 2 }
}
→ 200 { "code": 0, "data": { "run_id": 10231, "status": "queued" } }
```

**示例：WebSocket 推送**

```json
{ "type": "run_start",   "run_id": 10231, "case_count": 8 }
{ "type": "step_result", "case": "登录后查询订单详情", "step": "用户登录",
  "status": "passed", "elapsed_ms": 143 }
{ "type": "case_result", "case": "登录后查询订单详情", "status": "passed" }
{ "type": "run_end",     "run_id": 10231, "status": "failed",
```

### 9.3 ⭐ 用例编辑器（本平台的核心价值所在）

这是「为什么不用 Git 管 YAML 就完了」这个问题的答案。设计要点：

1. **表单 + 源码双视图**：
   - 表单为主（步骤拖拽排序、接口选择、断言可视化配置）；
   - 右侧 **Monaco** 展示编译后的 YAML（M1 只读，M3 开可编辑）；
   - ⚠️ **源码可编辑时，保存必须严格反解析回结构化数据，解析失败即拒存**（见 4.2）；
2. **引用关系可视化**：步骤 1 的 `extract` 变量 → 步骤 2 的 `$var` 引用，自动连线提示；**未定义变量红色标记**（对应退出码 21）；
3. **单步骤即时调试**：不用跑完整个用例就能验证单步的请求与响应；
4. **断言配置器**：下拉选内置校验器 + 期望值自动推断类型，**从 UI 层杜绝 YAML 手写缩进错误**；
5. **提取配置器**：选提取对象（5 类）→ 填 jmespath/正则 → 自动生成变量名并注册到变量面板。

### 13.2 必须实测确认的 6 件事 —— ✅ 全部完成

> 完整证据见 **`docs/引擎实测记录.md`**。以下为结论摘要 —— **其中 ③ 的实测结果推翻了原方案的假设，是本次最重要的修正。**

| # | 待确认 | 实测结论 |
|:--|:---|:---|
| **①** | `--log-json` 的真实字段结构与 JSON 行格式 | ⭐ **双流分离**：引擎日志 → `stderr`（JSON Lines，字段全集见实测记录 2.1）；**请求/响应明细 → `stdout`（纯文本，非 JSON）**。原方案「stdout 只有 `hrp exit N`」的表述需修正（F1 修正版） |
| **②** | HTML 报告的真实输出目录 | `results/<YYYYMMDDHHMMSS>/report.html` —— **印证源码 `env.go`，官方文档写的 `reports/report-<时间戳>.html` 是错的**。且为**自包含单文件**，无外链资源，平台直接托管即可 |
| **③** | 断言失败时的退出码到底是不是 1 | ❌ **不是 1，是 2**。且 **2 是 Go panic 的退出码**，不是设计契约：`builtin/assertion.go:53` 未初始化 `*testing.common` → 断言失败即空指针 panic。**同时 summary.json / report.html 完全不产出**。→ 归因判别器与结果解析策略全面改写（6.3 / 6.6） |
| **④** | `hrp run` 传入目录时的用例发现顺序 | **字节序（ASCII）字典序 + 递归子目录**（`Z_upper` 在 `a_alpha` 之前）。扩展名白名单 `.yml`/`.yaml`/`.json`。**F5 假绿同时坐实**：畸形文件静默丢弃、零告警、退出码 0 |
| **⑤** | `--save-tests` 的 summary 文件路径与结构 | `results/<时间戳>/summary.json`，结构与字段名已逐字记录。**致命缺陷**：`details[].root_dir` 恒为空、**无任何源文件路径**；**断言失败时完全不产出** |
| **⑥** | `debugtalk.py` 首次执行的 venv 准备耗时 | **不用插件 = 零开销**（可完全绕开 Python）。用插件 = AST 扫描 ~800 ms + **全局 venv** `~/.hrp/venv` + `funppy` 重依赖链；本机实测**安装失败（5.4 s → exit 9）**，且即使依赖就绪，插件路径**无限挂起**（>2 min，hrp 无超时保护）。→ **M1–M4 不支持 `debugtalk.py`** |

**实测额外挖出的架构级约束（不在原清单里，但更重要）：**

| 发现 | 结论 | 落地位置 |
|:---|:---|:---|
| **批量失败传染** | `hrp run <目录>` 全有或全无 —— 一个断言失败 panic，后续用例不执行、整批结果丢失 | **一个用例 = 一个独立子进程**（6.5） |
| **URL 尾斜杠归一化** | 无查询串时自动补 `/` | 调试视图展示「最终生效 URL」（F9） |
| **`locate plugin failed` 噪音** | 每用例每次一条 warn，与插件无关 | 日志视图白名单过滤 |
