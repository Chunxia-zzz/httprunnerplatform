## BUG-001：数组下标断言的「实际值」恒为空（nil）

**级别**：高 —— 击穿平台最核心的承诺。

### 现象

用例断言 `body.data[0].name` 失败时，运行详情页「断言明细」表里：

```
#  检查表达式            校验方法  期望值              实际值    结论    来源
1  body.data[0].name     eq        BitcoinXXX(string)  (nil)    未通过  平台重建
```

「实际值」是空的、「结论」列也不给原因，失败原因一栏只写「期望 BitcoinXXX，实际 」（实际值处为空）。而**真实值是 `Bitcoin`**。

### 复现步骤

1. 项目 48 建一条用例，步骤 `GET https://api.alternative.me/v2/listings/`
2. 加断言：检查表达式 `body.data[0].name`，校验方法 `eq`，期望值 `BitcoinXXX`（**故意写错**）
3. 执行 → 打开运行详情 → 看「断言明细」
4. 观察到「实际值」是 `(nil)`

> 为什么"故意写错"是必须的：断言**通过**时引擎自己会给出断言明细（`Rebuilt=false`）。只有断言**失败**时引擎会 panic、不产出 summary.json，平台才需要自己用响应快照**重建**明细 —— 缺陷只在这条路径上暴露。

### 影响范围

`body.xxx[0].xxx` 这类**数组下标**断言全部失效。这不是边缘场景：列表类接口（订单列表、标的列表、商品列表）几乎都返回数组，是最常见的断言写法。而且失效方式是**静默的**——不报错，只是"实际值"为空，用户会以为平台算不出来，进而不再信任失败明细。

### 根因（两层，必须都修才能恢复）

**第一层：路径切分不认识 jmespath 的方括号下标**

`internal/parser/eval.go` 的 `evalOne` 原来用 `strings.Split(path, ".")` 切路径，`data[0]` 被切成一个**整段键名** `"data[0]"`，在 map 里当然找不到这个键，于是返回 nil。

这里有一个**互斥死结**：

| 写法 | 引擎（jmespath） | 修复前的平台 |
|:---|:---|:---|
| `body.data.0.name` | ❌ 语法报错 `SyntaxError: Expected identifier, lbracket, or lbrace`，随后 panic | ✅ 能解析 |
| `body.data[0].name` | ✅ 正常执行 | ❌ 解析不出实际值 |

也就是说：**引擎能跑的写法平台解析不了，平台能解析的写法引擎跑不了**。而引擎侧 `check` 字段走的就是 jmespath，方括号是数组下标的唯一合法写法，所以必须让平台向引擎对齐。

> 关于 jmespath 的正反两次探针与原始日志，已正式收入 [引擎实测记录.md](引擎实测记录.md) 的 **A24**（`A23` 是「`hrp convert` 真实行为」，两条编号不同）。

**第二层：chunked 响应体的原始报文体不是干净 JSON**

`decodeBody` 原来直接把响应体丢给 `json.Decode`。但 httpx 打印的是**原始报文**，`Transfer-Encoding: chunked` 的响应体长这样：

```
4904                                   ← 十六进制块长度（原始报文的一部分）
{
	"data": [ ... ]
}
0                                      ← 结束块
```

`json.Decode` 读到 `4904` 会**当成一个裸数字解析成功**（不报错！），于是 `root` 变成一个 `json.Number`，所有 `body.*` 路径全部取不到值。

这一层的危害更大也更隐蔽：**症状和第一层完全一样**（都是"实际值 (nil)"），但根因毫不相干。只修第一层，真实场景下依然是空的。

### 修复

| 文件 | 改动 |
|:---|:---|
| `internal/parser/eval.go` | 新增 `splitPathExpr`（L295）：按 jmespath 语义切分 —— 支持 `data[0]`、`[0]`、`data[0][1]`、引号键 `["a.b"]`，并保留纯数字段 `data.0` 的兼容 |
| 同上 | `evalOne`（L97）的 body 分支补上 `body[` 前缀判断（原来只认 `body.`，导致 `body["data"][0]` 直接落到"平台无法重建"） |
| 同上 | `decodeBody`（L210）先判断响应体是否以 `{` / `[` 开头；不是则用新增的 `extractJSONValue`（L256）抠出最外层 JSON 再解析 |
| 同上 | `lookupPath`（L344）保持不变：段是"键"还是"下标"由**当前节点的类型**决定，所以两种切法都能落到同一处 |

`extractJSONValue` 取「第一个 `{` 或 `[`」到「最后一个配对的 `}` 或 `]`」。这么做而不去实现一个完整的 HTTP chunked 解码器，是因为收益比更高：不必关心每个分块的十六进制长度，天然容忍开头的封帧行与结尾的 `0`。

### 回归证据

**新增夹具 `internal/parser/testdata/assert_fail_https/`** —— 直接取自验收现场那次真实执行（run 61）的产物，`exit_code = 2`、无 `summary.json`、响应为 chunked 传输。两个 bug 的成因在这一个夹具里齐全，是最有说服力的回归基准。

**新增单测（`internal/parser/eval_test.go`，8 组）**：

| 测试 | 锁住什么 |
|:---|:---|
| `TestSplitPathExpr_切分规则` | 13 种表达式的切分结果（含方括号、纯数字段、引号键、畸形输入） |
| `TestSplitPathExpr_不因畸形输入崩溃` | `[`、`data["`、`[[` 等畸形输入不 panic |
| `TestRebuildAssertions_数组下标能取到真实值` | 8 个场景，核心是"期望写错时必须报出 `Bitcoin`" |
| `TestRebuildAssertions_根是数组时也能取下标` | 响应体顶层就是数组（`body[0].name`） |
| `TestRebuildAssertions_数组下标失败时给出可读原因` | 失败原因里同时含期望值与实际值 |
| `TestRebuildAssertions_多断言时数组下标失败会中止后续` | 与引擎执行顺序一致，后续标"未执行到" |
| `TestDecodeBody_剥离chunked封帧` | 剥封帧生效 + **对照组**：真非 JSON 的响应体照旧报错 |
| `TestDecodeBody_裸标量响应体仍可解析` | 剥封帧不能把"体本来就是数字"搞坏 |
| `TestExtractJSONValue_抠出最外层JSON` | 8 种输入（含 chunked 封帧、前后噪声、只有单侧括号） |

**现场验证**：重建后端 → 复现原场景（改用例 90 期望为 `BitcoinXXX`）→ run 63 的断言明细变为：

```
断言  body.data[0].name  eq  期望 BitcoinXXX  实际 Bitcoin(string)  未通过  平台重建
说明  期望 BitcoinXXX，实际 Bitcoin
```

之后把用例 90 恢复成正确期望，run 64 通过。

## BUG-002：失败运行的「最终生效 URL」协议被篡改成 http

**级别**：中 —— 不至于算错结果，但会让人误以为引擎改写了协议，损害对平台的信任。

### 现象

运行详情页同一张步骤卡片上，两行信息自相矛盾：

```
最终生效 URL   http://api.alternative.me/v2/listings/
用例声明        https://api.alternative.me/v2/listings/
```

协议从 `https` 变成了 `http`。

### 复现步骤

1. 用例步骤写 `https://api.alternative.me/v2/listings/`（**绝对地址、明确 https**）
2. 加一条**会失败**的断言（或任何导致步骤未正常结束的失败）
3. 打开运行详情 → 看「最终生效 URL」

只在**失败**运行下出现：成功时 `summary.json` 里有引擎给出的权威 URL，平台直接用那个，不重建。

### 影响范围

只看 URL 无法判断协议，用户可能据此以为"是不是请求被降级成 http 了"。此外 `strings.Contains(host, ":443")` 的写法还会把 `example.com:4430` 误判成 https。

### 根因

`internal/parser/parse.go` 的 `reconstructURL` 把 scheme 当成了**猜**的事：

```go
scheme := "http"
if req.Proto == "HTTP/2" || strings.Contains(strings.ToLower(req.Host), ":443") {
    scheme = "https"
}
```

而 stdout 里打印的请求行**几乎总是** `HTTP/1.1`（httpx 的明文调试输出），`Host` 头也不带端口：

```
-------------------- request --------------------
GET /v2/listings/ HTTP/1.1
Host: api.alternative.me
```

两个条件都不满足 ⇒ 一个 `https` 用例**必然**被渲染成 `http`。

### 修复

改为**有依据地推导**，优先级从高到低（`internal/parser/parse.go`）：

| 优先级 | 判据 | 实现 |
|:---|:---|:---|
| 1 | 用例声明的 URL 里的字面 scheme | `schemeFromDeclared`（L323） |
| 2 | 响应块里的传输层描述：`Connected via TLSv1.3` / `Connected via plaintext` | `schemeFromTransport`（L340） |
| 3 | 报文快照的 Proto / 端口启发式 | `schemeFromSnapshot`（L362），`Contains` 改 `HasSuffix` |

为什么第 2 级（传输层证据）必须存在：推荐写法是用环境变量 `$base_url/v2/listings/`，此时**声明值里根本没有 scheme**，第 1 级会落空。而 httpx 恰好会打印实际用了什么传输层 —— 这是"事实上走了什么协议"的直接证据，比任何启发式都可靠。

`reconstructURL` 签名相应变为 `reconstructURL(req, resp, declaredURL)`，调用点在 `buildSteps` 里传入 `decl.URL`（YAML 中声明的原始 URL）。

### 回归证据

**新增单测（`internal/parser/parse_test.go`，3 组）**：

| 测试 | 关键用例 |
|:---|:---|
| `TestReconstructURL_协议推导优先级` | 9 个场景，核心是"声明是 https 时，请求行写着 HTTP/1.1 也不能报成 http"；另含 `:4430` 不能误判成 https（锁住 `Contains` → `HasSuffix` 的改动） |
| `TestSchemeFromDeclared_只认http与https` | 大写 `HTTPS`、`ftp://`、`$var`、`//a.com` 等 8 种输入 |
| `TestSchemeFromTransport_从响应块识别协议` | TLSv1.3 / TLSv1.2 / plaintext / 无 / nil |

**真实夹具端到端**：`TestParse_真实HTTPS失败夹具_同时回归两个bug` —— 一个测试同时锁住 BUG-001 与 BUG-002。

**现场验证**：run 63 的「最终生效 URL」与「用例声明」现在**两行一致**，都是 `https://api.alternative.me/v2/listings/`。

## BUG-003：最终生效 URL 没有来源标注（原 OBS-001）

**级别**：中 —— 与 BUG-002 是同一处的两个面：协议修对了，可信度却仍然无从判断。

### 现象

运行详情页的步骤卡片里，两处**同类产物**的标注待遇不同：

```
最终生效 URL   https://api.alternative.me/v2/listings/          ← 无任何来源标注
用例声明        https://api.alternative.me/v2/listings/

断言明细
 #  检查表达式            校验方法  期望值              实际值            结论    来源
 1  body.data[0].name     eq        BitcoinXXX(string)  Bitcoin(string)   未通过  平台重建 ← 有标注
```

断言那行的「平台重建」标签是有意为之的（见 BUG-001 的说明）；而**同一个失败运行**里，`final_url` 同样是平台用 stdout 报文快照拼出来的，界面上却看不出这一点。

### 复现步骤

1. 项目 48 建一条用例，步骤 `GET https://api.alternative.me/v2/listings/`
2. 加一条**会失败**的断言（如把 `name` 的期望写成 `BitcoinXXX`）
3. 执行 → 打开运行详情 → 看「最终生效 URL」那一行：地址正常显示，但没有任何"这是谁给的"的提示
4. 同一张卡片往下看「断言明细」的「来源」列：写着「平台重建」

### 影响范围

只看界面，用户**无法判断失败运行里的 URL 有多可信**。这一点在 BUG-002 修好之后反而更要紧：协议现在是正确的 `https` 了，看上去"完全对"，于是没有人会怀疑它其实是平台拼出来的 —— 而对某些场景（如重定向、URL 归一化）平台重建值与引擎真实值可能并不等价。断言有来源标注、URL 没有，是同一个「不假绿」原则上的**一致性缺口**。

### 根因

`internal/parser` 其实**已经算出了** `FinalURLSource`（`"summary"` / `"reconstructed"`，见 `internal/parser/types.go:127`），但：

1. `model.StepResult` **没有这一列**，`insertCaseLayers` 落库时自然丢失；
2. 于是只有**单步调试**接口（`internal/service/debug.go:93` 的 `DebugStep`）返回它 —— 因为那条路径直接用 parser 的 `StepOutcome`，没经过数据库；
3. 前端 `types.ts` 里恰好**只有 `DebugStep` 声明了** `final_url_source`，于是在类型层面看着"字段是有的"，而运行详情页用的 `StepResult` 类型里根本没有它。

结果就是：数据在内存里活着，一落库就没了，界面上永远看不到。

### 修复

| 文件 | 改动 |
|:---|:---|
| `internal/model/model.go` | `StepResult` 新增 `FinalURLSource` 列（`size:16; not null; default:''`），JSON 名 `final_url_source`。string 列带 `default:''` 是安全的 —— 不带默认值的坑只针对**布尔**列（见 [数据库设计.md](数据库设计.md) 的说明） |
| `internal/service/run_suite.go` | `insertCaseLayers` 落库时赋值 `clip(st.FinalURLSource, 16)`。单用例执行与用例集执行共用这一段，所以两条路径同时生效 |
| `internal/service/run.go` | `CaseStepsDetail` 用 `Find(&steps)` 直接读表，加列后**自动**带出，无需改动 |
| `internal/api` | 无需改动：`StepResult` 的结构体 tag 即出参 |
| `web/src/api/types.ts` | `StepResult` 补 `final_url_source: string` 并写明三态语义；`DebugStep` 的该字段改成**可选**（后端是 `omitempty`，空来源时字段不出现，原来的非可选声明与实际不符） |
| `web/src/components/StepDetail.vue` | 「最终生效 URL」后按来源挂标签：`reconstructed` → 橙色「平台重建」，`summary` → 灰色「引擎」；各自带 tooltip 说明是哪种取值路径 |
| `docs/数据库设计.md` | 3.12 加列 + 第 2 节枚举字典补 `step_result.final_url_source` |

**迁移**：`repo.Migrate` 走 GORM `AutoMigrate`，加列在启动时自动完成，无需手写 DDL。旧数据该列取空串 `''`，前端按"未知来源"处理 —— 不标注，而不是猜一个。

### 回归证据

**新增单测（`internal/service/run_test.go`，1 组）**：

| 测试 | 锁住什么 |
|:---|:---|
| `TestInsertCaseLayers_URL来源必须落库` | **两层**一起验：落库层（`summary` / `reconstructed` 真的进了表）+ **接口层**（`CaseStepsDetail` 真的返回给前端）。只验落库会漏掉"存了但没查出来"这种更隐蔽的断链 |

**现场验证**：重建后端（启动日志可见 AutoMigrate 自动执行 `ALTER TABLE step_result ADD final_url_source`）→ 用脚本把用例 90 的期望临时改成 `BitcoinXXX` 跑一次失败执行，再改回 `Bitcoin` 跑一次通过执行，形成对照：

| 运行 | 状态 | `final_url_source` | 断言行的 `rebuilt` |
|:---|:---|:---|:---|
| run **66** | failed | `reconstructed` | `true`（平台重建） |
| run **67** | success | `summary` | `false`（引擎） |

界面侧（真实浏览器 CDP 验收）：run 66 的步骤卡片「最终生效 URL」出现橙色「平台重建」，run 67 同一位置显示灰色「引擎」——与断言明细的「来源」列口径一致。截图：`bug003-run66-failed.png` / `bug003-run67-passed.png`。

> 存量数据（run 63 及更早）该列为空串 `''`，前端按"未知来源"处理 —— 不做标注，也不推测。重跑一次即可得到正确值。

## BUG-004：0 条断言时归因理由仍写「全部断言通过」（原 OBS-002）

**级别**：中 —— 假绿的反面不是"报错"，是**在一行字里同时给出两个矛盾结论**。

### 现象

用例 89（`validate: []`，一条断言都没有）执行成功后，运行详情的归因理由显示：

```
归因：通过
全部断言通过          ← 0 条断言时说这句话
```

而**同一条用例**执行静态校验，平台给出的是：

```
warning / NO_VALIDATE / "没有断言的步骤只能验证「请求发得出去」，无法验证「结果对不对」"
```

一边说「只能验证请求发得出去」，一边说「全部断言通过」。用户读完这两句，不知道该信哪个。

### 复现步骤

1. 项目 48 建一条用例，只写一个请求步骤（`GET https://api.alternative.me/v2/listings/`），**不加任何断言**
2. 执行 → 打开运行详情 → 归因区显示「全部断言通过」
3. 回到用例编辑页执行校验 → 得到 `NO_VALIDATE` 警告

### 影响范围

0 条断言的用例**永远是绿的**，而且归因文案主动给了一句"验证过了"的暗示。这不是"结果算错"，而是**让用户误以为已经验证过**——本系统最该避免的假绿。注意归因本身**没有错**：引擎确实正常跑完了（exit=0），判成 `pass` 是对的，错的是**理由文案**。

### 根因

`internal/model/model.go` 的 `AttributionReason` 只拿到一个归因字符串：

```go
case AttrPass:
    return "全部断言通过"    // 无条件返回，没有考虑断言条数
```

断言条数在这个函数的可见范围之外，而在调用方（`RunService.CaseResultViews`）里也没人去查 —— 原先的 `CaseResult` 模型上只有 `step_total` / `step_passed`，没有任何断言维度的统计。

### 修复

| 文件 | 改动 |
|:---|:---|
| `internal/model/model.go` | 新增 `AttributionReasonWith(a string, assertTotal int)`，`AttributionReason(a)` 保留为"条数未知"的薄封装（不打断既有调用点）。新增哨兵常量 `AssertTotalUnknown = -1` —— **用负数而非 0**：0 是一个有意义的取值（该用例确实没写断言），两者话术必须不同 |
| 同上 | `AttrPass` 分支按条数三分：未知 → 通用文案；**0 条** → 与 `NO_VALIDATE` 同口径（点明"没有声明任何断言 / 只验证了请求发得出去"）；>0 → 「全部 N 条断言通过」，给出可核对的数字 |
| `internal/service/run.go` | 新增 `assertionCounts(runID)`：对 `assertion_result` 表按 `case_result_id` 做**一次 GROUP BY**（与 `stepStatusCounts` 同样避免 N+1）。没有断言的用例不会出现在结果集里，按 map 零值拿到 0 —— 正是想要的语义，**不要**兜默认值 |
| 同上 | `CaseResultView` 新增派生字段 `assert_total`（断言条数）与 `no_validate`（是否一条都没有）。刻意**不落库**：派生值一旦入库就有机会和明细不一致（与 `step_failed` / `step_error` 同一约定） |
| `web/src/api/types.ts` | `CaseResultView` 补 `assert_total` / `no_validate` 并写明语义 |
| `web/src/views/RunDetailView.vue` | 归因提示在 `no_validate` 时由 `info` **降级为 `warning`**，标题追加「无断言」橙标；用例描述区新增「断言」一项，无断言时显示橙色「未设置」 |

### 回归证据

**新增单测（`internal/model/model_test.go` 2 组 + `internal/service/run_test.go` 1 组）**：

| 测试 | 锁住什么 |
|:---|:---|
| `TestAttributionReasonWith_断言条数三态` | 未知条数返回通用文案（不返回空）；**0 条时文案绝不出现「全部断言通过」**且必须含"没有声明任何断言 / 请求发得出去 / 结果对不对"（与静态校验同口径）；N 条时给出「全部 N 条断言通过」；**非 pass 归因的文案不随条数变化** |
| `TestAssertTotalUnknown_哨兵是负数` | 防止有人把哨兵改成 0 —— 那会让"没查过"与"确认 0 条"重新混为一谈 |
| `TestCaseResultViews_零断言时归因降级` | 同一次执行里造两条**都是 pass** 的用例（A 无断言 / B 两条断言全过），要求 `assert_total`、`no_validate` 算对，且两者文案必须能区分开（跨用例串台、统计漏算都会在这里暴露） |

**现场验证**：重建后端后实测两个对照点：

| 运行 | 用例 | `assert_total` | `no_validate` | `attribution_reason` |
|:---|:---|:---|:---|:---|
| run **59** | 89 `listing`（无断言） | `0` | `true` | 用例执行成功，但这条用例没有声明任何断言 —— 只验证了「请求发得出去」… |
| run **67** | 90 `listing_assert`（1 条断言） | `1` | `false` | 全部 1 条断言通过 |

界面侧（真实浏览器 CDP 验收，13 项断言全绿）：run 59 的归因提示是**橙色警告** + 「无断言」标记，用例描述区「断言」显示橙色「未设置」；run 67 同位置是 `info` 色、写「全部 1 条断言通过」、「断言」显示「共 1 条」。截图：`bug004-run59-no-validate.png` / `bug004-run67-with-assert.png`。

## ENV-001：本机代理导致 curl 访问 localhost 返回 502

**级别**：—（**不是产品缺陷**，是环境问题） | **状态**：已记入文档

### 现象

起服务后 `curl http://127.0.0.1:8127/healthz` 返回 **502**，但 `netstat` 明确显示端口在 LISTENING，浏览器访问也正常 —— 一度误判"服务没起来"。

### 根因

本机存在环境变量 `http_proxy=127.0.0.1:59504`，`curl` 把发给 localhost 的请求也走了代理，代理回 502。

### 处置

已在 [用户验收指南.md](用户验收指南.md) 的「常见坑」表里补上解法：访问本地服务一律加 `--noproxy '*'`。

## 维护约定

- **新发现的缺陷先记录，再决定修不修**：现象、复现、根因（文件+函数）、影响范围四要素齐全，才算一条合格的记录。

- **状态要跟着改**：修好了把状态改成 `已修复`，并补上回归证据；决定不修要写清原因，不要留空。
