## 0. 已确认的决策

| # | 决策项 | 结论 | 理由 |
|:---:|:---|:---|:---|
| 1 | 用例集是否支持嵌套（用例集里放用例集） | **不做** | 组织层级保持三层已够用；真正的需求是「复用」，由用例引用用例解决 |
| 2 | 用例集遇错行为 `OnFailure` | **continue（跑完再汇总）** | CI 里一次看到全部失败，不用「修一个跑一次」；接口用例本该互不依赖 |
| 3 | 服务重启期间错过的调度点 | **不补跑，但在页面标出「上次错过」** | 补跑会造成「我明明没动它，它自己跑了一堆」；标出来则保证「错过」不被静默吞掉 |
| 4 | CI Token 存储方式 | **只存哈希，创建时显示一次** | 库里没有明文，拖库拿不到可用 token；CI 重签成本极低 |

## 1. 为什么不做「用例集嵌套」

「嵌套」在这个项目里指两件完全不同的事，必须分开判断：

### 1.1 组织嵌套：用例集 ⊂ 用例集 —— 不做

代价有四，且都不是虚的：

| 代价 | 具体表现 |
|:---|:---|
| **循环引用** | A 装 B、B 装 A → 展开时死循环，必须在保存时做环路检测 |
| **结果聚合** | 同一用例同时属于「支付」和「退款」，跑「支付」时算 1 次还是 2 次？通过率的分母是什么？ |
| **重跑去重** | CI 最常用的动作是「只重跑失败的用例」，树形下要先拍平再去重 |
| **UI 复杂度** | 树形多选（带半选状态）比平铺多选难写难用得多 |

现有 schema 也**是按扁平设计的**：`SuiteCase` 只有 `CaseID`，没有指向用例集的字段；
`TestSuite` 没有 `ParentID`。做嵌套要先动表结构。

### 1.2 复用嵌套：用例引用用例 —— 单独一步做

场景：「登录」（POST 拿 token + 提取 token）被 20 个业务用例重复用到。
没有它 → 登录接口加个验证码要改 20 个地方。

schema **已经留好**：`TestStep{StepType:"testcase", RefCaseID}`，
`model.StepTestCase = "testcase"` 常量在，前端 `dict.ts` 里连中文标签「引用用例」都有。
编译器目前明确拒绝：

```go
case model.StepAPI, model.StepTestCase:
    return ys, decl, fmt.Errorf("步骤类型 %q 在 M1 尚未开放（计划在 M2 支持接口/用例引用）", st.StepType)
```

**分层结论**：组织层级保持 `计划 → 用例集 → 用例` 三层；缺口在**用例级复用**，
它改的是编译器与执行器的核心契约，因此与本文的编排层分开排期（第 7 节）。

## 2. 用例集

### 2.1 数据模型

沿用现有 `TestSuite` / `SuiteCase`，两处调整：

```go
type TestSuite struct {
    SoftBase
    ProjectID   uint64  // 归属项目
    Code        string  // 标识，创建后不可改（与用例一致）
    Name        string
    Description string
    ExecuteMode string  // sequential | parallel；M2 只实现 sequential
    OnFailure   string  // abort | continue；默认 continue（决策 2）
    Timeout     int     // 整批超时（秒），0 = 不设
}

type SuiteCase struct {
    Base
    SuiteID uint64
    CaseID  uint64
    Seq     int
    // ⭐ 新增唯一索引 (suite_id, case_id)
}
```

**唯一索引 `(suite_id, case_id)` 是刻意的**：同一用例在一个用例集里出现两次会
直接破坏「通过率的分母」，而这类重复几乎都是误操作。需要「跑两遍」的场景
由 M3 的参数化（`ParamDataset`）解决，不靠同一条成员重复两行。

> **为什么 `ExecuteMode` 保留 `parallel` 字段但不实现**
>
> 平台的一条硬约束是「一个用例一个独立子进程」（实测 A2：断言失败会让引擎
> panic，目录模式下整批结果丢失）。并行意味着同时起多个子进程，与
> `engine.max_concurrency` 的信号量耦合，且会让归因与日志归属变得难以判断。
> M2 只做串行；字段先留着，避免以后加并行要动表。

### 2.2 执行语义

一次用例集执行 = **1 条 `RunRecord(target_type=suite)` + N 条 `CaseResult`**。

```
RunRecord{ target_type:"suite", target_id:<suite_id>,
           expected_case_count:N, actual_case_count:M, count_mismatch: ... }
  ├─ CaseResult{ seq:1, case_id:..., status:"pass" }
  ├─ CaseResult{ seq:2, case_id:..., status:"fail", attribution:"system_under_test" }
  └─ ...
```

关键约束（全部继承自既有的执行器设计）：

1. **每个用例独立编译、独立子进程**。编译逐条进行：邻居用例写坏了不挡住本条
   —— 与单用例执行保持同一条原则（见 `run.go` 的注释）。
2. **一次执行共用一个运行工作区**：先逐条编译进项目持久层工作区，
   再 `CopyFrom` 一次到 `{root}/runtime/runs/{run_id}`，然后逐条跑。
   每个用例的产物落在自己的 `CaseArtifactsDir` 下，互不覆盖。
3. **`OnFailure=continue`**：某条失败后继续下一条；最终 `RunRecord.status` 取
   「有 fail 则 failed、有 error 则 error、全部 pass 才 success」的**最坏值**，
   并在 `error_msg` 里给出失败用例清单。
4. **用例数对账**：`expected_case_count = N`（打算让引擎跑的条数），
   `actual_case_count = 实际真正启动的用例数`。二者不等时**强制升为 `error`**
   （沿用 `decideRun` 的规则，实测 F5：畸形用例被引擎静默丢弃时退出码是 0
   且 `success=true`，只看退出码会给出假绿）。

#### 2.2.1 `expected` 的口径（实现时修正了两处）

初版把 `expected` 定义成「成员总数」，实现后跑冒烟发现不对，修正如下：

| 情形 | 是否计入 `expected` | 理由 |
|:---|:---|:---|
| 正常成员 | ✅ | 我们打算让它跑 |
| 已禁用成员 | ❌ | 用户主动关掉的，跑不到是预期内的 |
| 已删除成员 | ❌ | 用例都不存在了，谈不上「打算跑」；它靠 `status=error` 表达 |
| 编译失败 | ✅ | 本来打算跑，但没启动过 ⇒ 由对账抓出来（同时也已是 error） |
| `abort` 之后未执行的 | ❌ | 见下 |
| 取消之后未执行的 | ❌ | 见下 |

**⭐ `abort` 与取消时必须把 `expected` 收缩到实际尝试过的条数。**
否则每一次 `abort` 都会额外报一句「对账不一致」，把真正的信号（引擎静默丢弃）
淹在一堆噪音里。对账要抓的是「我没让它停，它却没跑」，不是「我让它停的」。

同理，`status=canceled` 时不再叠加对账文案。

### 2.3 成员里出现已软删 / 已禁用的用例

**不静默跳过**。执行前逐条检查：

| 状态 | 处理 |
|:---|:---|
| 用例被软删除 | 记为一条 `status=error` 的 `CaseResult`，`error_msg` 写明「用例已删除」；`actual` 不计入 |
| 用例 `status=disabled` | 记为 `status=skipped`，不计入 `actual` |
| 用例属于其它项目 | 编译期即拒绝（保存成员时校验，不放到这里才发现） |

理由：什么都不写的话，用户只会看到「预期 10 条实际 8 条」却不知道少了哪两条 ——
**报出来，而不是让人去猜**。

#### ⭐ 实测修正：「已删除成员」在页面上走不到

写完执行逻辑后跑端到端冒烟，发现 `DELETE /cases/{id}`
**在用例被用例集引用时直接返回 `40003`**（`case.go`：
`用例 %q 被 %d 个用例集引用，请先移出用例集`）。

这条保护是对的：与其让用例集悄悄少一条，不如在删除时就挡住。
但它意味着 2.3 表格里的第一行**只能由防御性代码兜住**，正常操作路径到不了 ——
因此这一分支的测试放在 `internal/service/run_suite_test.go` 里直接操作 DB
（绕过 HTTP 层的保护），不放在端到端冒烟里。

## 3. 测试计划与定时

### 3.1 数据模型（含一处技术债修复）

现有 `TestPlan.SuiteIDs` 是 `size:255` 的逗号字符串。两个问题：
① 大约 40 个 ID 就写满；② 删除/重命名用例集不会级联，会留下悬空 ID。

改为关联表：

```go
type PlanSuite struct {
    Base
    PlanID  uint64
    SuiteID uint64
    Seq     int
    // 唯一索引 (plan_id, suite_id)
}
```

```go
type TestPlan struct {
    SoftBase
    ProjectID    uint64
    Name         string
    EnvID        uint64
    TriggerType  string  // manual | cron
    CronExpr     string  // 5 段，见 3.2
    Timezone     string  // ⭐ 新增：IANA 时区名，如 Asia/Shanghai
    NotifyConfigID uint64
    Timeout      int
    Enabled      bool
    // 运行态
    LastRunID      uint64  // 最近一次执行（含被跳过的）
    LastFiredAt    *time.Time
    LastMissedAt   *time.Time  // ⭐ 最近一次**被跳过**的调度点（决策 3）
    LastSkipReason string      // "上一轮仍在执行" | "服务未运行"
}
```

### 3.2 cron 规格

- **5 段**：`分 时 日 月 周`（`robfig/cron/v3` 的 `ParseStandard`）。
  不用 6 段带秒 —— 测试计划最细到分钟已经足够，秒级只会让「为什么它在跑」
  更难解释。
- 支持 `@daily` / `@hourly` / `@every 30m` 等描述符带来的便利，但**保存时归一化**：
  存的就是用户填的原文，预览时再算出「下次执行时间」给他看。
- **校验在保存时做，不等到调度器启动才失败**：cron 表达式写错是最常见的错误，
  让它落在 `POST /plans` 的 40000 上，而不是变成一个永远不跑的计划。

### 3.3 时区 —— 最容易埋雷的一处

**每个计划自带 IANA 时区名**（默认 `Asia/Shanghai`），调度器按该时区解释 cron。

不绑时区的后果很隐蔽：服务器在 UTC 上跑，用户填 `0 9 * * *` 以为「早上 9 点」，
实际是 UTC 9 点（北京时间 17 点）。这类错误不会报错，只会让所有计划静默错位，
而发现它往往要等好几周。

### 3.4 调度器的三条硬规则

1. **重入保护（必须第一天就做）**：上一轮还没跑完、下一个调度点到了 →
   **跳过**，记 `LastSkipReason = "上一轮仍在执行"`。
   不做的话，一个跑 40 分钟的用例集配 `*/5 * * * *` 会把执行堆成山，
   而且每一条都在抢 `max_concurrency` 的槽位。
2. **不补跑错过的调度点（决策 3）**，但记录 `LastMissedAt` 并在页面显示
   「上次调度点被错过：…」。保证「错过」这件事不被静默吞掉。
3. **调度器只在单实例下成立**：多实例部署时每个实例都会触发同一个计划。
   M2 按单实例做，**这条必须写进部署文档**。以后要多实例，靠数据库行级锁
   抢「调度权」解决，不在本次范围。

## 4. CI Token

### 4.1 按项目签发（决策 1）

`APIToken.ProjectID` 已存在。

> ⭐ **必须强制校验请求里的 `project_id` 与 token 所属项目一致**。
> 这是「按项目签发」的全部意义 —— 不校验的话，一个项目的 token 能触发
> 任意项目的执行，按项目签发等于白做。

### 4.2 只存哈希（决策 4）

```go
type APIToken struct {
    Base
    ProjectID  uint64
    Name       string
    TokenHash  string  // ⭐ 替代原 Token 明文：sha256(hex)
    Prefix     string  // ⭐ 展示用前缀，如 hrp_ci_a1b2c3d4
    Scope      string  // "run:trigger,run:read"
    ExpireAt   *time.Time
    LastUsedAt *time.Time
}
```

**为什么是 sha256 而不是 bcrypt**：

bcrypt 的意义在于**抗暴力破解**（密码有猜测空间，要故意算慢）。
CI Token 是 32 字节随机数（64 位 hex），没有猜测空间 —— 用 bcrypt 只会
让每次触发都白付 100ms 的 KDF 开销，换不到任何安全性。sha256 足够，
且能走唯一索引直接查库，快。

**创建时只显示一次**，之后只能看到 `Prefix`。忘了就重签 —— 对 CI 而言
重签的成本远低于「明文长期躺在库里」。

### 4.3 端点与鉴权

| 项 | 约定 |
|:---|:---|
| 前缀 | `/open`（与 `/api/v1` 分开：CI 触发不走会话体系，语义与限流都不同） |
| 鉴权 | `Authorization: Bearer <token>` 或 `X-HRP-Token` |
| 触发 | `POST /open/runs` — 请求体与 `/api/v1/runs` 一致 |
| 项目校验 | 请求体 `project_id` 必须等于 `token.ProjectID`，否则 40300 |
| 同步等待 | 默认异步返回 `run_id`；`?wait=1&timeout=<秒>` 走阻塞等待 |

**默认异步，同步选配**：CI 里的长连接很容易被网关/代理掐断，让流水线挂在一个
HTTP 请求上等 20 分钟是脆弱的。默认给 `run_id` 让流水线自己轮询，
`?wait=1` 留给「跑几秒就结束」的冒烟场景。

### 4.4 给 CI 一个能直接判成败的字段

```jsonc
// GET /open/runs/{id}/result
{ "code": 0, "data": {
  "status": "failed",
  "exit_code_for_ci": 1,       // ⭐ 0 / 1，pipeline 可直接用
  "passed": 8, "failed": 2, "error": 0, "skipped": 0,
  "count_mismatch": false,
  "failed_cases": [ { "case_code": "login", "attribution": "system_under_test" } ]
} }
```

不加这个字段，每条流水线都要写一段 `jq` 去解析 status 枚举，而且每个人写的
判断都不一样（有人把 `error` 当成功）。**给一个数字，别让人去猜语义**。

## 7. 不在本次范围：用例引用用例（另排一步）

- `step_type=api` 引用接口定义、`step_type=testcase` 引用用例，
  编译成 hrp 的 `api:` / `testcase:` 引用。
- **唯一的真坑是循环引用**：A 引用 B、B 引用 A 会让编译器死循环 ——
  比用例集嵌套更危险，因为它在**编译期**。必须在编译时做 DFS 环路检测并报 `50003`。
- 变量传递与 `export` 机制另议（被引用用例的 extract 如何导出到父用例）。

## 8. 验收标准

| # | 标准 | 验证方式 |
|:---:|:---|:---|
| 1 | 能建用例集、勾选成员并调整顺序，重复加入被拒（40001） | 单测 + 浏览器 |
| 2 | 用例集执行产生 1 条 RunRecord + N 条 CaseResult；某条失败后后续仍跑完 | 单测（含引擎） |
| 3 | 用例被软删时执行报 error 而不是静默少跑；`count_mismatch` 生效 | 单测 |
| 4 | cron 表达式非法时保存即报 40000，不会得到一个永远不跑的计划 | 单测 |
| 5 | 计划自带时区，同一个 cron 在不同时区算出的下次执行时间不同 | 单测 |
| 6 | 上一轮未结束时新调度点被跳过并记录原因，不堆积 | 单测 |
| 7 | CI token 只能触发本项目；跨项目请求返回 40300 | 单测 + 浏览器 |
| 8 | CI token 创建后库里无明文；再次查看只剩前缀 | 单测（直查 DB） |
| 9 | 流水线拿到 `exit_code_for_ci` 能直接判成败 | 接口验证 |
| 10 | 单文件产物下新增页面可用（`go:embed` 覆盖新 chunk） | 浏览器（打 exe） |
